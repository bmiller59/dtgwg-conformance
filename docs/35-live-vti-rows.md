# Live rows: the ceremonies and core run against VTI's service containers

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

The ceremony rows of [docs/27](27-kw-vti-ceremonies.md), [docs/30](30-onboarding-vetting-ceremonies.md) and [docs/32](32-rooms-ballot-ceremonies.md) ran against VTI's in-process hosts. This page records the same scenarios, and the core run, against VTI's **service containers**: the community service (`vtc`) and the agent service (`vta`) of the buildathon starter kit, images built from the pinned ref (`26d0da81`, vtc-service 0.20.0, vta-service 0.72.0), started with `docker compose` and driven only through their public doors. Every outcome here is an outcome of ceremonies run together (one pair, one carrier, one date); none is a conformance count and none is added to a PASS total.

## 1. What a live row is, and the stand-ins it needs

- **One stack, one network.** One compose project (`bamvtilive`: the VTA on one local port, the VTC on another) is used for the whole run. It is never taken down and brought up between scenarios. Between scenarios the one service under test is stopped and started with its data volume restored from a snapshot taken once (a throwaway container with no network does the restore), so no compose project, network or port is created or removed.
- **Why the state is restored, not left in place.** Leaving the state in place and restarting the container was tried first (`live-agent2/kvc.up-pass1-state-in-place`, `-pass2-restart-reset-acl-revoked`, and the first community pass). It makes later scenarios start from the earlier ones' effects (a previous grant makes `FC-KVC-001` see an effect it should not; the applicant is already a member in `FC-MBR`), so those passes are kept as records of the attempt and are not used. The control layer still has the restart-only mode (`LIVE_RESET=restart`) for a run that can accept it.
- **The control layer** (`src/adapters/vti-live/`) answers the control routes the in-process adapters expect, over a live container, and refuses with the reason where the service offers nothing (a refusal is the finding). It holds the class D stand-ins:
  - sessions are real logins with keys the suite holds (a service that has no bearer-minting shortcut);
  - the access list is prepared on the wire as the kit's administrator before the consent gate is on, and the policy (enforcement, approver sets) is the service's config file edited in its data volume, then a restart;
  - the community's `public_url` is edited to `https` (the origin the service checks), and the DID document handed to the ceremony is read as the community would publish it after the transport change its own documentation describes (service endpoints on the door's origin moved to the public origin; keys untouched);
  - **not observable on a live service:** the push engine's records, the credential store, the proof verifier. Scenarios that need them end `inconclusive` or `skipped` with that reason, never `completed`.
- **The wallet's DID resolver (class D).** The keyring-wallet host resolves DIDs through a small resolver shim that knew only `did:key` and `did:peer:0`. The live community is a `did:webvh`, so every wallet read of the community refused before sending anything. The shim now reads the last state of the log the service serves at the DID's address (the log's hash chain and proofs are not verified; the row measures the wallet's use of the document, not a `did:webvh` resolver).

## 3. Classification of what did not complete

- **Wallet refusals against the live community (`K reads refused`, `FC-MBR`, `FC-IDV`, `FC-AUT`, first live pass).** Cause: the wallet is not at fault in either case.
  - `FC-MBR`, `FC-IDV`: **class D, stand-in artefact.** The wallet host's resolver could not resolve a `did:webvh`, so the wallet's own manifest read failed before any document was built. Fixed in the harness (section 1); the rows were re-run and now agree with the reference row and with the in-process rows.
  - `FC-AUT-001` to `007`: **class D, deployment address.** The wallet's sign-in reads only `https` service endpoints with no port (the wallet's `isCandidateEndpoint`, which follows the out-of-band sign-in rules; its error is "This community doesn't offer sign-in from the app"). A community container on a local port publishes an endpoint with a port, and a local container cannot publish one without. The reference party, which does not apply the no-port rule, completes the same scenarios against the same container. No wallet change is warranted, and none was made (ledger: no change). Not run: a community published at an address without a port.
- **`FC-MBR-006`, `FC-MBR-007` (wallet rows, first re-run).** The live DID document lists the community's `VTCRest` service, so the wallet read the join manifest over its own REST fast path, outside the carrier the scenario records; the scenario's replay index (`1`, the second document) then did not exist: class D. Re-run with the document the shim hands the wallet not listing `VTCRest`, so the manifest travels on the carrier as in the in-process rows (`KW_LIVE_REST=on` leaves it in). The first re-run is kept outside the run set as `live-community2/mbr-idv-kw*-restpath`.
- **`FC-MBR-007`.** A submission with a tampered proof is answered `permissionDenied` (HTTP 403, "Trust Task proof verification failed") where trust-task-error 0.6 declares `proofInvalid` for "a proof was present but failed verification". **Class A against the original container**, on the reference and both wallet rows. The in-process pin host answers `proofInvalid` for the same bytes, so the difference is in the live door's holder-authentication layer. Not fixed: the specification text does demand the code, but the fix is in that layer of the service and could only be checked with a rebuilt container; the vector keeps the specification's code. Recorded for the owner to decide.
- **`FC-KVC-003`, `011`, `012`.** Class A, as in the in-process rows: the agent answers `permissionDenied` "signer is not a member of approver set" (003), `taskFailed` (011) and `permissionDenied` "challenge does not match" (012) where the specifications declare `notAnApprover`, `noPending` and `challengeMismatch`.
- **`FC-KVC-013`, `101`.** Skipped by capability: the live agent serves decision 0.2 only and offers no executor leg.
- **`FC-DEV-002` to `005`.** Class A, the same four failures the in-process row `avl.up.vti-up` records: the agent answers `taskFailed` with the declared code only inside the message (`details.reason` `conflict`, `not_found`; for `005` the revoke answers `acl/revoke:subjectNotPresent`), where the scenarios expect the declared code in the `code` field.
- **`FC-STU-001`, `002`, `005`.** Class A: the agent holds a gated grant with a `taskFailed` carrying the approve request (the error shape deployed agents use today), the wallet answers, and the retried grant makes the wallet receive two documents (`001`), none (`002`, a refusal on the phone), and `challengeUnknown` for an unprompted approve (`005`). `003` and `004` end as specified.
- **`FC-VLT-001`.** Class D, inconclusive: the credential store is not readable on a live service's wire, so "the agent holds one credential" cannot be observed. The first pass recorded it as failed ("V stores 0 credential"); the adapter now reports the observation as unobservable and the scenario ends inconclusive (D281).
- **A reference approver on `avl`.** `FC-ACL`, `DEV`, `VLT`, `STU` need a `member-phone`; the reference party does not play it, so all 23 scenarios are skipped ("role not offered"). Not a row; the record is kept outside the run set.

## 4. Core run against the live community

The core run (`--vectors vectors`, registry, proposed and candidate channels) against the container is the surface `vti-live` of the at-a-glance page, in run `2026-11-20-vti-live-core`. It supersedes the 2026-11-14 live runs. One core vector fails: `CEX-031` (credential-exchange/request): the service answers `malformedRequest` where the vector expects `unknownOffer` or `invalidProof`. **Class C, pending**: it depends on which code the specification means for a well-formed request naming an offer the community does not hold; the question is open and the vector is unchanged.

The coverage vectors (`vectors/coverage`) were started against the live community and did not complete: the service stopped answering (it accepted connections and returned an empty reply) during the `config/*` vectors. Nothing from that run is recorded.

## 5. What is not run

- The wallet's sign-in against a community published at an address without a port.
- The push engine, credential store and proof verifier observations (a live service offers none on its wire).
- The executor leg of task consent, and decision 0.3 (the live agent serves 0.2 only).
- The live `plain` and `2l` runs: `plain` was started and stopped after several minutes, because the service's anonymous rate limit paces the run at about one refused document every five seconds and it was far from done; `2l` was not started. Nothing from them is recorded.
- The live coverage run (section 4).

## 6. The second pass of the agent rows (2026-11-20)

- **Stack.** One compose project `bamvtilive`, one network, one volume `bamvtilive_vta-data`, the ref-tag image `vta-buildathon:26d0da81` (never `:local`), created once and kept to the end of the run; the old project was already gone. No project, network or volume was created or removed between scenarios.
- **Pristine baseline, checked before the first scenario.** With the daemon stopped, a throwaway container with no network listed the ACL (`vta acl list`): one entry, the kit's administrator; `policy.enforcement = false`, no approvers, no approver sets. The snapshot every scenario restores was taken from that state. A session is not logged in before that (a login seals the offline commands of the service).
- **Reset.** Stop, restore the volume from the snapshot by a throwaway container with `--network none`, start; one scenario per invocation of the runner, since the adapter holds policy state in memory.
- **Actor role.** The `avl` scenarios need the member's wallet to hold the admin role of the agent (`VTI_ACTOR_ROLE=admin`, as for the in-process agent in docs/32). The first pass of `avl` without it was refused (`permission denied: admin or initiator role required`) and is kept outside the run set.
- **Two harness fixes found on the way** (class D, D281): the consent gate's `enforce` route now gives the suite's identities their ACL entries before the gate is switched on (a grant is itself held for step-up afterwards, and the offline command is refused once the service is sealed), as the `policy` route already did; and an unobservable credential store ends a scenario inconclusive.
