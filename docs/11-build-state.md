# Build state: what exists and what is not built

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.


This is the detailed inventory of the parts of the suite, moved here from the repository README so the README can stay short. Dated run results are published separately and are not part of this repository (results/README.md is generated locally by `npm run regen` and is not published, [D959](decisions/06-runs-and-results.md#d959)).

## What exists

What exists (all under this folder, runnable):

| Part | Where | State |
|---|---|---|
| Vector format `tt-conformance-vectors/0.1`, JSON Schema, loader and validator, vector id scheme `<GROUP>-<NNN>` | `src/vectors/`, `schema/` | Proposed format. The validator is hand-written and a test keeps the schema file consistent with it; the schema is not itself executed. |
| Adapter contract (the JSON-RPC method set of docs/04 section 4 as TypeScript types, an in-process dispatcher, and the out-of-process client and server helper) | `src/adapter/` | Out-of-process adapters are driven with `--adapter stdio:<command>` (newline-delimited JSON-RPC) or `--adapter http:<url>`. The wire contract with JSON examples is docs/04 section 4. Optional helper methods: `verifyProof` (capability `proofVerify`) and `verifyReceipt` (capability `receiptVerify`, group RCPT). |
| Example adapter server: the reference adapter served over stdio or HTTP, the model for an implementation's own server | `src/adapters/example-server/server.ts` | `test/rpc.test.ts` runs the whole vector set through it on both transports and requires the in-process results. |
| Reference adapter on the published `@openvtc/trust-tasks` 0.29.0 runtime: Tier 1 consumer behaviour, and Tier 2 `attested` behaviour (proof required, purpose pinned, signed replies, closed payload) for `did:key` Ed25519 / `eddsa-jcs-2022` | `src/adapters/reference/` | Serves one "carrier" task, plus ceremony behaviour for `vrc/relationships/propose` and `issue` as the counterparty and receiving party on `did:key` (hold, consent, relationship-DID bookkeeping, credential checks, receipt by read-back). Also `vrc/relationships/witness-share` (bundle verification in the order of docs/10 section 4, stored witnessed credential, receipt by read-back), a ceremony-document family (begin, approve, reset and an optional status task: hold, quorum, deadline, reset rules, verbatim retention; it supports both values of the declared `ceremony.proposerApproves` and a status variant that declares `ceremony.status`; the example server takes `--no-ceremony`, `--cosign` and `--status`), restart, a claim-store fault hook, and the proofs of a non-`did:key` implementation are verified from the DID document `provision` returns. It also serves the 3b-DTG tasks (`task-consent/request` as the approver device, `task-consent/decision` as the executor of a ceremony held for approvals, `credential-exchange/issue` as the holder, `credential-exchange/present` as the verifier; the example server takes `--no-dtg`). |
| Runner: capability gating (SKIP, never PASS), tier selection, exceptions file with owner and expiry (KNOWN-FAIL; stale and expired exceptions fail the run), CLARIFY, advisories, capability matrix as JSON and Markdown | `src/runner/` | The command line runs Tiers 1 and 2 for every adapter by default (`--tier 1\|2` runs exactly that tier). The matrix Markdown always prints each implementation's declared window, the Tier 2 sub-group roll-up and the advisory count. Also: rebase mode for an implementation whose clock cannot be set (`clockFree`), a per-run id salt, declared acceptance windows, and the vacuous-pass rule for matrix cells (below). Recorded exceptions are counted in results/README.md, Recorded differences. |
| Clock-free peers: an adapter that cannot set its clock declares `clockFree` (not `clock`); the runner takes real time as each vector's clock start and applies the vector's relative offsets to it. Vectors that need exact, millisecond-boundary or multi-offset clock control are SKIP with a reason, never PASS | `src/runner/clock.ts`, docs/04 section 7 | The reference adapter has a clock-free mode (`reference-clockfree`, example server `--clock-free`); results are identical in process, over stdio and over HTTP. |
| Run salt: deterministic document ids carry a per-run salt, so a second run against a durable peer does not replay the first run's ids | `src/runner/build.ts`, docs/04 section 7 | Random per run by default; `--salt <value>` reproduces a run, `--salt ""` leaves ids unsalted. |
| Declared acceptance windows: the 5 min / 60 s / 30 day numbers are Tier 2 `profile-window` pins, not framework text. An implementation declares the window it enforces (`capabilities.window`), or the runner is given one (`--window`); Tier 1 time vectors use it, and the matrix prints it and reports a difference from the pins | `src/runner/window.ts`, docs/04 section 6 | A window of 10 minutes is measured against itself and reported as a difference, not a failure; the `profile-window` fixture rows that pin 5 minutes are SKIP for it. `reference-window10` demonstrates it. |
| Vacuous-pass rule: a matrix cell is green only when its anchor positive vectors pass; otherwise it is annotated | `src/runner/matrix.ts`, docs/04 section 8 | An implementation that refuses everything passes its negative vectors but is not shown green. |
| Non-vacuity: every negative vector names deliberate mutants of the reference adapter, and a test proves each mutant fails it (a mutant that violates a SHOULD is declared under `advisoryMutants` and must raise an advisory) | `src/adapters/reference/mutants.ts`, `test/reference.test.ts` | Each pair is run in every reference configuration it applies to; each ceremony pair is checked in every reference configuration it runs in (both `ceremony.proposerApproves` values, and the status variant for the status vectors). |
| Vector groups of the core family: ENV, RSP, ERR, ID, LIF, CTRL, TIME, DUP, PRF (the ES256 proof fixtures are SKIP for the Ed25519-only reference), VRC-PRO, VRC-ISS, NS, AUTHZ, TD, WSH, DIS, BND (SKIP unless the adapter declares the `https` binding; BND-007, the status table, is Tier 2 `attested`), 2PC (trigger actions in docs/04 section 12.1), CER (the ceremony-document family of docs/04 section 11.4, SKIP unless the adapter declares it; CER-015 and CER-016 need `ceremony.status`), TC and CEX (the 3b-DTG groups of docs/04 section 11.5: `task-consent/{request,decision,granted}` and `credential-exchange/{issue,present,query,offer,request}`, SKIP unless the adapter declares the Type URIs and the helper actions they need), and RCPT (the `trust-ceremony-receipt` verifier rules of docs/04 section 11.6, all Tier 1, some CLARIFY, SKIP unless the adapter declares the optional capability `receiptVerify`). Further families: plain, emit, emit-more, witness, 2l | `vectors/` | Counts by family, channel and tier are generated: results/README.md, Vector families. DUP-103 needs the carrier class `openPayload`, which a closed-payload implementation does not declare. Pass against the reference adapter. Authored in `scripts/generate-vectors.ts`; the JSON is generated and a test checks it is current. |
| VTI agent service adapter: a Rust host runs VTI's `MockVta` (the VTA's real router, dispatcher, handlers, stores and response signer) in one process, reached over its HTTPS door on loopback | `src/adapters/vti-inprocess/` | Results: results/platforms/vti.md. Nothing in VTI is changed. |
| VTI community service adapter (`verifiable-trust-infrastructure`): a VTC over its HTTPS door (`POST /v1/trust-tasks`), carrier `notifications/notify/0.1`, `clockFree`, `attested`, no bearer, `handled` derived from the wire; offline ACL seeding of the harness actors. Two drivers: live over HTTPS (`src/adapters/vti/index.ts`) and in process against the service's own test host (`src/adapters/vti/launcher.ts`) | `src/adapters/vti/`, `scripts/vti-seed-acl.ts` | Results: results/platforms/vti.md; the live-service run is older than the in-process runs. The differences are recorded as exceptions or CLARIFY (docs/05 section 1.4). |
| VTI sending-side adapter: documents built by VTI's own client code, checked by the emit families | `src/adapters/vti-emit/` | Results: results/platforms/vti.md. Types it cannot build are listed with reasons in `not-built.json`. |
| keyring-wallet adapter ("logic over a shim carrier"): the wallet's own trust-task code run under its jest setup behind an in-memory carrier, process `Date` faked by the shim; not wire interop | `src/adapters/keyring-wallet/` | Results: results/platforms/keyring-wallet.md. |
| keyring-wallet over real DIDComm: the wallet agent behind a Credo DIDComm agent (v1 by default; v2 is a separate, experimental leg) | `src/adapters/keyring-wallet-didcomm/` | Results: results/platforms/keyring-wallet.md. |
| keyring-wallet witness server over DIDComm (`vectors/witness`) | `src/adapters/witness-server/` | Results: results/platforms/keyring-wallet.md. |
| Task-force fixtures reused as oracle (`fixtures/proof`, `fixtures/consume`) | `vectors/imported/` | Copied unchanged with a SHA-256 per file. The source revision is not recorded (see `vectors/imported/PROVENANCE.json`). |

**Third implementation: truststackers.** The suite has no adapter for it: the original repository has no Trust Task boundary the suite can reach (results/platforms/truststackers-original.md). The plan in [docs/06](06-truststackers-conformance-plan.md) describes the work that would be needed. The remaining engineering work and the one plainly open question (who contacts the task force) are in [docs/07](07-status-and-open-questions.md) section 4.

Not built:

- Vector group IDK and the roadmap families after the benchmark (approver attestations, vetting, membership, data rooms). WSH-022 and WSH-023 are reserved, not built. The ceremony vectors assert nothing about the `continuation` value of a hold that names a status task or about the content of the status response beyond its type (docs/04 section 11.4), and do not test the initiating side of a ceremony. BND does not test the client side of the binding, the 403, streaming and in-flight 202 rows are covered only inside other vectors or not at all (docs/04 section 11.3); DIS does not test the discoverer side. The VRC groups test only the receiving side; the IUT-initiated direction (the implementation emitting `propose` or `issue`) is not covered.
- Some Tier 1 vectors are CLARIFY (profile rules, open questions and points the specifications do not settle, never gating); each vector's `clarify` text says why, and the reference adapter's CLARIFY count per family is in results/README.md, Coverage. See docs/04 section 11.1 and docs/07.
- Not built: the `ceremony` member vectors on ordinary documents (CRM), the recorder side of `trust-ceremony-receipt`, and the interop runner, recorder and promoter, and the transport matrix.
- ES256 (`ecdsa-jcs-2019`) verification in the reference adapter: those four fixtures are SKIP. `did:key` is the only identifier method supported.
- Vector ids: the design table of docs/04 section 11 uses design ids that differ in places from the files (for example the ENV numbering). The files are authoritative for what runs; docs/04 section 11.1 lists the ids as built. Group and id numbering is proposed.

Vectors marked `skipIfOptional: attested` (and `exactTier` Tier 1 vectors) are SKIP against an attested server: full Tier 1 coverage of an implementation with both modes needs a second, non-attested run. Runs that share an `implementation` in their capabilities are merged into one matrix row, so the vectors the attested run skips are covered by the other run, and the row names any still uncovered (docs/04 section 4.2).
