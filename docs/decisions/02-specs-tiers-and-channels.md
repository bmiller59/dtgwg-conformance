# Specifications, tiers and channels

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

Tiers and advisories, specification sources and channels, the latest-versions focus, task-force alignment and pins. Part of the [design rationale register](README.md).

## Specification sources and channels

<a id="d76"></a>**Decision 76 (in force).** Draft specifications and open or unmerged pull requests may be cited, always with their status (draft, pull request number, commit). Where: `tfRef.status`; docs/04 section 18.7.

<a id="d79"></a>**Decision 79 (in force).** Every vector cites a TF-repository artifact (main, a draft or an open pull request) or is in channel `candidate`; anything else is removed or excluded from every run. `candidate` is the advisory channel for vectors with no home in the TF repository that one or a few platforms implement; such a vector records `implementedBy`, the local text and an adoption note, and is not an endorsement. Advisory results never change a gating count, and a changed pinned digest is reported as spec drift. Why: a test suite meant for the task force must rest on the task force's own text. Where: docs/04 section 18; `test/tfref.test.ts`; `npm run resolve-tf-refs`. The ceremony family follows it through [decision 39](04-ceremonies-governance-and-exceptions.md#d39). The governance probes are candidates by channel but counted apart ([probe class](#probe-class)).

<a id="probe-class"></a>**Governance probes are a `probe` class (in force).** The five governance probes (`vectors/governance/gov.json`) carry `probe: true` beside `source`; they stay in channel `candidate`, and wherever channel counts are shown they are counted as `probe`, never as candidates. The marker is allowed only on a candidate, and the governance loader refuses a probe without it. Why: a candidate is behaviour one or a few platforms implement and might adopt ([decision 79](#d79)); the probes are suite instruments under [decision 77](04-ceremonies-governance-and-exceptions.md#d77), and counting them as candidates inflated that column. Rejected: a fifth channel (channels describe the maturity of the cited text, which for the probes is the same as for any candidate). Where: `probeMarkerErrors`, `countedClassOf` in `src/vectors/source.ts`, `loadProbes` in `src/governance/probes.ts`, `familyTable` in `src/glance/docs.ts`; [docs/04 section 18.1](../04-suite-design.md#181-the-source-member), [docs/17 section 4](../17-governance-probes.md#4-the-probes-vectorsgovernancegovjson-group-gov); `test/probe-class.test.ts`.

<a id="d78"></a>**Decision 78 (superseded by 79).** The 23 witness-share (WSH) vectors rest on suite-local text (docs/10). They first moved from `registry` to `proposed`; under decision 79 they are `candidate`.

<a id="promotion"></a>**Promotion criteria (in force).** A vector gates (`registry`) only when its rule is in TF text on main and quoted, the reference passes and a named mutant is caught, it ran with the same verdict on three consecutive recorded runs (with `run.json`) on at least two surfaces, it has no live-network timing dependency or a recorded retry policy, and it is not CLARIFY, quarantined or excluded from runs. CLARIFY becomes asserted only when TF text settles the point; the vector is then re-checked and re-run before it gates. Each promotion is its own reviewed commit and a gating-set change (major, docs/04 section 20.2). Why: a single unreviewed promotion, or a vector that gates on network luck, would fail a platform for the suite's fault. Rejected: promotion on a maintainer's judgement alone; promotion on one surface. Where: docs/04 section 18.9.

<a id="quarantine"></a>**Flaky vectors are quarantined, with an expiry that fails (in force).** A vector whose verdict varies for the same implementation and inputs is first checked for a suite cause (fixed, not quarantined). Otherwise it gets an entry in `exceptions/quarantine.json` (vector, implementation, reason, observed on, owner, expiry); its result is QUARANTINED: run and shown, but advisory, in no count and never in the exit code. An expired entry makes the result FAIL, like an expired exception. Why: one bad run on live DIDComm or HTTPS must not fail a platform, and quarantine must not become a silent exemption. Rejected: automatic retries until a pass (hides real failures); a KNOWN-FAIL for flakiness (a KNOWN-FAIL records a reproducible difference). Where: `src/runner/quarantine.ts`; `test/quarantine.test.ts`; docs/04 section 18.9.

<a id="clarify-classes"></a>**CLARIFY has a class, an age and an exit (in force).** Every CLARIFY vector carries `clarifyClass` (`spec-silent`, `spec-inconsistent`, `vector-overreads`, or `unclassified` where its text supports none), `clarifySince` (first commit date, or `0.1.0-draft` when it predates the history) and `clarifyQuestions` (drafted TF question ids, empty until drafted), from the hand file `vectors-src/clarify-classes.json`. `vector-overreads` is fixed by the suite (rewrite, move channel or retire); the other two wait on the task force. Why: CLARIFY must not become a permanent parking place that hides disagreement. Rejected: one undifferentiated CLARIFY (no exit, no backlog for the task force). Where: docs/04 section 18.10; `src/vectors/clarify.ts`; the vector generators; `test/clarify-classes.test.ts`; the CLARIFY-by-class block in results/README.md.

<a id="traceability"></a>**Reverse traceability is generated from the pinned texts, outside check:docs (in force).** The normative statements (BCP 14 keywords) of the task-force texts the vectors cite are extracted at the pinned commit and listed with the vectors that cite their lines, by section only, or not at all, in `results/traceability.md`, with the limits stated on the page. Why: forward citations show a vector is grounded; only the reverse shows what no vector covers. The page needs a local task-force clone, which is not tracked, so `npm run check:docs` does not check it; `npm run traceability -- --kit <clone> --check` does. Rejected: a hand-kept requirement inventory with ids such as `FW-7.2-11a` (manual and drifts with every draft); fetching the texts from the network. Where: docs/04 section 18.11; `scripts/traceability.ts`; `src/traceability/extract.ts`; `test/traceability.test.ts`.

Version pins: framework 0.6.0, error 0.6, https 0.3, tsp 0.1, `@openvtc/trust-tasks` 0.29.0, recorded in `capabilities.pins`. Private task types use the URN form `urn:<NID>:<prefix>:spec:<slug-segments>:<MAJOR.MINOR>` (the framework grammar requires a prefix; the private prefix `tasks` is proposed, not confirmed). Where: `src/adapter/contract.ts`; `slugOf` in `src/runner/engine.ts`.

## Latest versions are the focus

Suite side of the latest-version direction (project owner decision, 2026-11-20). Nothing was pushed, filed or sent. Run records stay outside the repository.

- <a id="d245"></a>**Target is the latest version (D245, in force).** Old task versions are out of focus: the target is the latest version of each slug in the task force repository (main, open pull requests, branches). In the coverage matrix every version carries `focus`: `focus` (the latest non-retired version of its slug: 862 of 1,420 versions), `older` (below the latest: 510; shown as "older (non-focus)") or `retired` (the latest is retired: 48 slugs, "retired (out of focus)"). Headline counts cover the focus versions only. Older versions and their vectors stay in the repository and stay runnable (`--channels`, the existing `proposed` profiles), are labelled non-focus, never gate and are never in a headline count. Why: measuring the versions nobody is moving to hides the work of reaching the latest. Where: `src/coverage/matrix/focus.ts`, `build.ts`, `render.ts`; `results/coverage/README.md`; STATUS.md, results/README.md.
- <a id="d246"></a>**Retired latest and `supersededBy` (D246).** A slug whose latest version is retired is out of the target; the version its `supersededBy` front-matter names (a slug, or a slug and version: the slug is what counts) is the target instead, taken as the latest of that slug and followed through retired successors (at most eight hops; a cycle or a slug not in the repository gives no successor). 47 of the 48 retired latest versions resolve to a successor; `trust-task-ok/0.1` (a reply type) names none and is reported as such, not guessed. `vta/webvh/dids/{update,rotate-keys}` (latest 2.x retired, 1.0 and 1.1 live) follow the rule as written, so they are out of the target here; whether to keep 1.0 and 1.1 in scope (plan decision D241, an assumption awaiting the project owner) is not decided by this rule.
- <a id="d247"></a>**VTI main layout and pin (D247).** On upstream `origin/main` (`71d524572`) the community has no `DISPATCHED_URIS` table (VTI #2579): routing is `routing.rs` plus `on!(routes, <payload path> => handler)` in each `vtc-service/src/trust_tasks/*_tasks.rs`. The matrix scanner reads those registrations (`onRegistrations`: a full spec-crate path, or an alias bound by the file's own `use`, never one a test module re-imports with `use super::`) and the witness service's `SERVED` table; 378 community URIs instead of 36. The command takes `--vti-pin <label>` (labels the input) and `--vti-rev <sha>` (for the read-only archive, which has no git history). The matrix is regenerated on `main`. Voting (`vti-voting`) and the VTN crate have no dispatcher table the scanner reads: their versions stay "pinned, no dispatcher entry found" (an upper bound), as the plan said.
- <a id="d248"></a>**Reach classes platform and scope (D248).** A SKIP at the latest non-retired version is class `platform` (or a suite limit); a SKIP of an older or retired version is class `scope` (outside the target). Implemented on the reach pages, not as a new at-a-glance skip class: `scripts/gap-reach.ts` and `src/coverage/reach.ts` (`reachClass`, and `other-version` split into `superseded` = VTI names only newer versions, `behind` = VTI is below this version, `mixed`), the matrix's per-platform table, the platform pages (`latestLine`) and `results/skip-classes.json` (note). The at-a-glance headline classes (not applicable, not reached, version mismatch) are unchanged; the page gains the table "Latest versions only" (what ran at the focus, older and retired versions). Assumption: the project owner may prefer `scope` as a fifth at-a-glance class; that would change every at-a-glance count and was not done.
- <a id="d249"></a>**Vector focus (D249).** A vector is `focus` when it names any focus version, `older` when it names only older versions, `retired` when its only tasks are retired latest versions, `none` when it names no registry task. Of 8,567 vectors: 4,857 focus, 3,244 older only, 303 retired only, 163 none (the plan's figures, reproduced). A vector that names both an older and a focus version counts as focus.
- <a id="d250"></a>**Stale figure corrected (D250).** docs/28 said VTI serves the same task at another version for some gap versions and refuses a superseded version as `unsupportedType`; that figure did not hold against upstream main and is withdrawn. Against upstream main, with the 702 gap versions: 7 declared, 139 feature-gated, 48 sent only, 384 not named, 124 "another version" of which 108 are older than what VTI speaks (`scope`), 10 below it (5 focus, `platform`) and 6 mixed.
- <a id="d251"></a>**Witness vectors not retargeted (D251, resolved by D290).** The 66 witness vectors (38 `WIT-*` on session 0.1 or submit 0.1, 28 of `vectors/witness`: WSS 11, WSB 7, WSD 10 on discovery 0.1) target older versions (witness 0.2 and discovery 0.4 are the latest); WIT-015 and WIT-016 are the only 0.2 vectors. They are labelled non-focus and left unchanged until the project owner says to retarget; the list and what retargeting needs are in docs/29.
- <a id="d252"></a>**Coverage page and docs/22 (D252).** The version-grain family table gains "Latest versions used (focus)", "Older versions used (non-focus)" and "Latest with any vector"; the earlier columns stay. The focus class is read from the committed `results/coverage/matrix.json`, so the matrix is regenerated (`npm run coverage-matrix`, not part of `npm run regen`) before the pages are.

## Task-force alignment

- <a id="d920"></a>**Alignment tool and advisory alignment set (D920, 2026-11-23).** `npm run tf-alignment -- <checkout> [--ref <revision>]` measures what the Trust Tasks repository holds against what the vectors use (examples, fixtures, ceremony definitions, tasks, cited files and hashes, the generators' recorded pins), read-only and deterministic; output `results/tf-alignment.json` and `.md` ([docs/tf-alignment.md](../tf-alignment.md)). A new generator, `scripts/generate-alignment.ts`, writes `vectors/alignment/` (group TFA-INV): one advisory vector (channel proposed, profile tf-alignment) per snapshot task that sends the invalid examples no other set sends and that the task's own schema refuses, expecting a refusal (framework text 7.2 item 2). It is kept out of first-share figures: it is registered in `scripts/regen.ts`, and `scripts/generate-gap.ts` no longer counts it as a set that holds a task back from the gap families. The reference oracle passes the set; no platform was run. Ids: this section starts the D920 range; D910 to D916 are used twice elsewhere (two working logs each took them); this register does not renumber them.

## Task-force pins

- <a id="d950"></a>**One task-force commit for every pin (D950, 2026-11-23).** The manifest (main and kit), the invalid-example snapshot, the spec-hash table, the task facts and the imported fixtures' provenance were moved to the commit the gap snapshot, the completion extras and the scope inputs already named: origin/main `bd0c05013` (2026-11-19). The manifest was 43 commits behind and the kit pin 277 behind; the fixtures recorded no commit. `npm run check:pins` (`src/vectors/pins-check.ts`, tested in `test/pins-check.test.ts`, also run by `npm run check:docs`) fails when any recorded commit differs, is missing, or when the manifest does not name a full commit. Effect on the vectors: none removed and none added by the pin move (9,008 before and after; the 180 advisory alignment vectors of D951 are separate, 9,188 in all). Every vector's `tfRef.commit` now reads `bd0c05013`; 3,125 vectors changed only in a pin stamp (`tfRef.commit`, `tfCommit`, `inKit`). 201 vectors changed in more than a stamp: the 158 vectors of the layer-2 set (the line that cites the checkout now names `bd0c05013` and its date), 38 framework vectors (13 DUP and 25 TIME, whose pinned digest of the imported consumer fixtures changed because three fixtures were added), VC-VOTING-001 and -002 (they now carry a spec hash), and CV-AA-177, CV-AA-178 and EX-VTA-020 (the retirement below). The 16 task specifications newer than the old manifest were already in the gap snapshot, so they already had vectors and now resolve in the manifest. Two specifications the task force retired since (`vta/webvh/dids/list` 1.0 and `vta/webs/dids/list` 0.1) are listed retired by the manifest, so the side table `RETIRED_AFTER_PIN` was removed and the generic retired-spec rule (D901) names the real successor (`vta/dids/list/0.1`) in the exclusion of the three vectors that cite 1.0; the number of vectors excluded from every run is 467 before and after. No first-share figure moved: `results/coverage.md` and every other generated page are byte-identical. The spec-hash table now holds the 1,418 files the vectors cite (it held 717).
- <a id="d951"></a>**Widened alignment snapshot (D951, 2026-11-23).** `vectors-src/alignment/tf-snapshot.json` holds every task version of every family that lists invalid examples (1,415 versions). Only `scripts/generate-alignment.ts` reads it, so no other set can pick up a task version from it. An example is written only where it is a request entry (an entry marked `"variant": "response"` is an invalid reply and is never sent as a request), the task's own payload schema refuses it without `format` asserted, and no other set sends an equal payload as a request (`src/plain/invalid-examples.ts`). The advisory set (group TFA-INV, channel proposed, profile tf-alignment) holds 219 vectors and 797 examples; ids are kept, a new task takes the next number after the highest id ever issued, and a vector left with no example would stay as a tombstone. Measured with `npm run tf-alignment` at `bd0c05013` (figures in [results/tf-alignment.md](../../results/tf-alignment.md)): 4,235 of the 5,252 invalid examples are used (80.6%; 96.2% of the 4,401 request entries), 3,450 (65.7%) without the alignment set; none of the 851 response entries counts as used.
- <a id="d952"></a>**The alignment tool compared a vector's hash with the wrong file, and branch-only citations (D952, 2026-11-23).** The tool reported 23 cited files whose text hash had changed. It took the first spec path (in sorted order) mentioned anywhere in a vector's text and compared the vector's recorded hash with that file, so a vector that merely mentioned another specification was compared with the wrong one. It now compares only the file the vector itself cites. The real count is none: the only specification text change that matters in the pin move is the retirement of `vta/webvh/dids/list` 1.0 (front matter `status: retired`, `supersededBy: vta/dids/list/0.1`), and its three vectors were re-pinned with the reviewer's decision still-correct (wording only) and stay excluded from every run (D901). The 24 vectors that cite the three specifications that exist only on pull request 904 (`understanding` exchange, offer, seal 0.1) were already classified: channel `pr`, citing the head commit `96b1d70ea`, which still holds all three files and is not part of main. They stay provisional and are not presented as part of the standard; the tool now lists such files as branch-only, not missing.
- <a id="d953"></a>**Three new consumer fixtures imported, not wired (D953, 2026-11-23).** `consume/ext-critical.json`, `consume/ext-critical.schema.json` and `consume/extends-routing.json` are copied with checksums and the source commit (`bd0c05013`) is recorded in `vectors/imported/PROVENANCE.json`; the 36 files imported earlier are byte-identical. No vector is derived from them: the cases depend on a consumer's recognized-namespace set and on an extends chain handed to the runtime, neither of which a document sent over the wire can set, and the schema in the fixture is a test schema, not a task. See [tf-alignment.md](../tf-alignment.md) for the option left to the owner.
