# Vectors and coverage

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

Coverage families, uncovered families, vector completeness, gaps, older sets, witness vectors and registry promotion. Part of the [design rationale register](README.md).

## Coverage families (trust tasks keyring-wallet and VTI use)

Design: [docs/22](../22-coverage-families.md). The unit is a task type, one slug plus one version. These decisions were put to the project owner as nine open decisions (each with pros, cons and a recommendation) and adopted as recommended.

<a id="cv1"></a>**CV-1 Depth (in force).** Mechanics vectors (payload schema, declared policy, a valid request is not refused for an envelope reason) for every used type; behavioural vectors only where the Trust Tasks text states a rule, ordered by the 108 types both platforms use. Why: complete and honest, and every vector's claim is traceable to text. Rejected: mechanics only (says nothing of behaviour); behavioural only for the 108 (leaves 470 VTI-only types uncovered).

<a id="cv2"></a>**CV-2 Versions (in force).** Every version a platform serves or sends gets mechanics vectors through the generator; behavioural vectors only for the newest version and any version keyring-wallet uses. Rejected: newest only (a used older version would read as uncovered).

<a id="cv3"></a>**CV-3 Channel (in force).** `proposed` for a type with a Trust Tasks specification, `candidate` for one without; none is core, none gates, none counts in a headline or the exit code, and the families run only with `--vectors vectors/coverage --channels proposed,candidate`. Rejected: letting the draft-text vectors gate (the specifications are all draft and move).

<a id="cv4"></a>**CV-4 Family granularity (in force).** Eight families by domain: RM (rooms), VP (vetting, process attestation, voting), MB (membership and directory), CS (consent and step-up), SD (session, device, vault, keys, access, policy), AA (agent administration), CA (community administration), PW (peer ceremony wire). Each can be run, reviewed and reported alone.

<a id="cv5"></a>**CV-5 VTI-only administration (in force).** AA and CA are included, last, mechanics only: stateless probes (payload, recipient, proof); no valid-request probe; a destructive task (wipe, delete, purge, restore, remove, revoke, reset, rotate and similar) gets schema-invalid payloads only, and nothing is sent to a live service.

<a id="cv6"></a>**CV-6 Types with no Trust Tasks text (in force).** Ten used types have no specification: they get candidate vectors only where a local text exists (witness-share, the agent seeds and audit-retention tasks, the vault archive family); private keyring-wallet types and the VTI private namespace stay out and are listed as blocked. No semantics are invented.

<a id="cv7"></a>**CV-7 One ceremony runner (in force).** The scoped `tt-ceremony-scenarios/0.1` track carries every ceremony flow, existing and new; no second mechanism. Single-document ceremony checks are not used as a stand-in.

<a id="cv8"></a>**CV-8 Counting grain (in force).** Coverage is published at version grain beside the existing task grain, both definitions printed. The public number gets smaller; the "104 of 104" task-grain figure stays true at its own grain and is no longer the only one.

<a id="cv9"></a>**CV-9 Witness-server row (in force).** No wording about the witness server appears in the coverage pages until the witness server is re-run on the final suite; until then the row is labelled "recorded earlier". Satisfied on 2026-11-18: the witness server was re-run on the suite (both keyring-wallet states, DIDComm v1 and v2, channels registry, proposed and candidate) and the row now says so.

<a id="cv10"></a>**CV-10 Independence label (in force).** A vector generated from the registry schema is not independent evidence of that schema, because the platforms build against the same schema. Every coverage vector says which input it rests on (registry schema, or the task force's own invalid examples, or specification text) and each family page repeats the limit.

<a id="cv11"></a>**CV-11 Spec drift (in force; the schedule is open).** Each vector keeps its Trust Tasks commit and gains a hash of the normalised cited text and of the task schema ([docs/23](../23-spec-drift.md)). Hashes catch change, not correctness: a moved hash flags a vector SPEC-CHANGED (advisory, in no count, never in the exit code) until a reviewer re-pins it with a recorded decision. The check, `npm run check:spec-drift`, is run on demand before each measurement; no scheduled job is created. Alternative rejected: failing a run on drift, because a moved spec is not a platform failure. Implemented in `src/vectors/spec-hash.ts`, `spec-drift.ts`, `repin.ts` and the runner.

Open for the project owner: whether to schedule the check weekly. Recommendation: do not schedule yet; add a weekly reminder to run it only after the first real drift event, because until the task force changes cited text we do not know how often it happens, how noisy the check is, or whether a week is the right interval, and a schedule that fires on nothing is ignored by the time it matters. Pros of a weekly schedule now: drift is seen within days rather than at the next measurement, and the Spec pin line stays current without anyone remembering. Cons: it adds a standing job to maintain, it can flag text changes nobody has time to review (so the line goes stale anyway), and a flagged vector is advisory, so the cost of finding drift at the next measurement is low. Without a recommendation to the contrary, the check stays on demand.

<a id="cv12"></a>**CV-12 Extended payload builder (in force).** A coverage version whose valid payload the plain builder `example` cannot build gets one more attempt with `exampleExtended` (`src/plain/schema.ts`, `src/plain/pattern.ts`): a string built from its `pattern`, `oneOf` alternatives merged with the members of the enclosing schema, an open `minProperties` object, and a deeper nesting limit. The reason is that a version with no valid payload keeps only the task-force-example probes. The alternative rejected was changing `example` itself, which would change every plain, emit and 2L vector already generated. `example`'s own output is returned unchanged, probes of a version built only by the extended pass are numbered after every other probe of its group (the id ledger is append-only), and a placeholder member satisfies the schema without claiming what the task does. Implemented in `src/coverage/catalog.ts` and `scripts/generate-coverage.ts`; checked by `test/payload-builder.test.ts`.

<a id="cv13"></a>**CV-13 Version-grain coverage page and skip-class rules (in force).** `npm run regen` writes `results/coverage.md` (`scripts/coverage-pages.ts`, `src/coverage/pages.ts`) and the counts block of docs/22: per family and in total, the types used (keyring-wallet, VTI, both), the types with any vector (vectors joined on source slug and version), the types with a behavioural vector, and the vectors per group, beside the existing task-grain figure, both definitions printed. Recorded coverage runs are an optional input (`COVERAGE_RUNS_DIR` or `--coverage-runs`): without them the page prints the vector counts and says no coverage run is recorded, and `regen --check` does not fail; with them it adds, per run folder, the types that ran (a result other than SKIP) and the SKIPs by class. Advisory: never in a headline count, the catalog total or an exit code. The page names the limits (behavioural vectors only for the newest and keyring-wallet-used versions, none for candidate types, a census that mixes sent and received types), the independence label of CV-10, the wording rule (the strongest claim is that the suite ran against both with the same vectors), keeps truststackers (original) with no coverage run and the witness server labelled "recorded earlier" (CV-9). Skip classes: `results/skip-classes.json` rules may carry a `label` (not served by this surface, send-only, no counterpart, not reached by the suite). The 21 emit vectors of the keyring-wallet surfaces for types the wallet source builds but the suite adapter's emit flows do not drive are not reached (a suite limit), never not applicable; the existing cited-not-offered evidence rule still governs not applicable. A test proves every distinct SKIP reason of recorded coverage runs gets a class. Observed code (added later, still advisory): an advisory-channel result whose vector accepts `permissionDenied` beside a task code carries `observedCodes` (the code each error step saw) and, when every such step passed on `permissionDenied`, `acceptedOnlyGate`; the page splits PASS by them and prints "not recorded" for runs made before the field. Registry results are unchanged byte for byte. Alternative rejected: replacing the task-grain figure, because it is true at its own grain.

<a id="cv14"></a>**CV-14 The keyring-wallet denominator counts the types the wallet sends (in force, decided by the project owner on 2026-11-18).** The version-grain keyring-wallet headline counts the types the wallet's source **sends** (census `kw_role` `sent` or `both`), with the all-used figure (every type the source names) printed beside it, never alone. Why: a check of what a platform sends needs a type the platform sends; a type the wallet only receives, or only names in a rule list or comment, has no send to check, so counting it in the headline understates the share of what the wallet does that the suite covers and makes a SKIP on such a type look like a gap in the wallet. Rejected: the all-used figure as the headline, because it counts types the wallet only receives or only names. Rejected: dropping the all-used figure, because it is the figure the earlier pages printed and hiding it would hide the change. The roles come from the wallet's own source, read in the original tree, with the file and identifier for each type in [kw-roles-evidence.md](../../vectors-src/coverage/kw-roles-evidence.md); a role is changed only on what the source says. The task-grain list (`results/task-scope.json`) follows the same rule: on 2026-11-18 it gained the 21 tasks the wallet sends that it lacked, and the page prints the earlier task-grain figure (104 tasks) beside the new one so the change is explained, not hidden. Implemented in `src/coverage/families.ts` (`kw_role`, `kwSends`), `src/coverage/pages.ts` (headline, the all-used column, the earlier-figure line, the reconciliation) and `src/coverage/reconcile.ts` (the sent counts and the lists).

<a id="cv15"></a>**CV-15 One ceremony runner; scenario evidence is never a conformance count (in force as a design; phase 0 built on the reference adapter only).** The fifteen multi-step flows of the uncovered-tasks plan (FC-VRC, FC-WSH, FC-TCA, FC-CEX, FC-MAT and the ten new ones) are carried by one mechanism: the scoped `tt-ceremony-scenarios/0.1` track, run by one separate runner (`npm run ceremony`, `src/ceremony/`), not by a second mechanism and not by single-document ceremony vectors. Pros: one contract change (the optional `initiate` and `connect` methods and the `received` and `ceremony` observe queries, additive and capability-gated like `emit` and `observe.pushed`), one evidence kind. Cons: the flows that no reference can play wait for the platform phases. The runner is not part of the default run: its scenario files are in `vectors/ceremony-scenarios/` under their own manifest (`scenarios-manifest.json`, which no vector loader, catalog or count reads), its exit code is its own, and its results never enter a headline count, the catalog total or the suite exit code. A scenario that completes, or ends in the refusal it specifies (`ended-as-specified`), is reported per pair, carrier and date, with the label "ran together, one pair, one carrier, one date", and is never summed with vector counts, never called a pass count and never called interoperable without that qualifier. The evidence kind is `complete-ceremony`. The reference adapter and `reference-peer` may play every role only to show that the format and the engine are sound (every mutant ends a scenario in `failed`); that is not evidence about any platform and is never admitted to the interop ledger. Alternatives rejected: single-document ceremony vectors per flow now (weaker, and a second mechanism); one stage adapter that hosts every party (it hides independence and cannot hold two platforms); counting scenario outcomes as PASS (they are not conformance results). Detail: [docs/25](../25-ceremony-scenarios.md). Phases 1 to 3 (platform runs), the live carrier mode and the ledger 0.2 are not built.

<a id="cv16"></a>**CV-16 Seeded-state probe for held findings (in force; advisory).** A held finding is a platform answer the suite could not classify because the request named an object the platform does not hold. The probe re-asks it with the object present: each probe vector first creates the room, git namespace or key through the task the platform serves for it (`rooms/create` 0.2, `git-ns/namespace/bind` 0.2, `keys/create` 0.1), on the same signed path as every other step, then sends the held vector's payloads naming it. Why this and not a seeding call into the platform's store: the create tasks are reachable and non-destructive, so no write to a platform store is needed and the probe is a check of the platform's own handlers. The one host change is opt-in: the in-process VTC host runs the platform's own default-policy installation (the call `vtc` makes at start and the test-support state omits) and declares the optional capability `seed.defaults`; the agent adapter takes the actors' role from `VTI_ACTOR_ROLE` when set. Both are off by default, so no earlier run changes. The reference oracle gains a small state model for exactly these objects and two labelled mutants: `lookupFirst` (the order the original platform shows) and `noPayloadValidation`; a probe passes under the first and fails under the second, so a probe never decides the order and only shows whether the platform validates at all once the object exists. Five retired behavioural vectors whose stated code needed such an object are re-issued under new ids (their tombstones stay); the rest stay retired. Everything is channel `proposed`, outside every headline count, and a result is a statement about one platform's answer, not about a specification. Rejected: writing rooms or namespaces into a platform's store, because the probe would then test the host, not the handler. Implemented in `src/coverage/probe.ts`, `scripts/generate-probe.ts`, `src/adapters/reference/seeded-state.ts`, `src/adapters/vti/` and `vectors/probe/`; see [docs/22](../22-coverage-families.md#seeded-state-probe-cp).
