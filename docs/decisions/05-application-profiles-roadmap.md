# Application profiles roadmap

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

Roadmap decisions RD1 to RD7 on the application profiles. Part of the [design rationale register](README.md).

## Roadmap decisions RD1 to RD7

The application-profile (AP) structure: capability-gated profiles 2L-1 to 2L-5, task-consent as the core approval primitive, credential status and revocation as a named gap, rooms and messaging out of 2L, the plain-task probe first. Private keyring-wallet types are out of scope until specifications exist. Detail: [docs/16 section 2](../16-roadmap-and-decisions.md) and [proposals/2l-profiles-draft.md](../proposals/2l-profiles-draft.md).

| Id | Question | Outcome | Status |
|---|---|---|---|
| RD1 | One flat layer or profiles | Capability-gated profiles 2L-1 to 2L-5: access and approval; holder, device and push; notification and delivery; assurance; community lifecycle. A claimant claims only what it serves, as discovery already works. | decided |
| RD2 | Where approval sits | `task-consent/*` stays the core approval primitive, and `auth/step-up/*` is a 2L-1 member over it. `consent/*` (messaging-conversation consent) is not an approval primitive and is at most an optional, separately claimable member. `confirm/*` is retired and does not appear. | decided; placement of `consent/*` open |
| RD3 | Credential status and revocation | A named gap in 2L-4. No task is drafted from one implementation's HTTP status list; the gap is taken to the task force with evidence. | decided; revocation/status itself open |
| RD4 | Access control (`acl/*`) | In 2L-1, paired with governance declared through the `understanding` family (open draft pull request #904: `understanding/{offer,exchange,seal}`, `termsRef`). The profile defines mechanics only and carries one declared pointer to the deployment's governance document. | decided; per-grant citation open, and so is whether to name `understanding/*` at all (the family may be renamed) |
| RD5 | Rooms and messaging | Out of 2L (a domain profile). The one related pull request is open, with no second implementation. | decided |
| RD6 | Who gets vectors first | The plain request-reply tasks of 2L-1 and 2L-2 (acl, policy, vault, device, auth), through the plain-task probe | done |
| RD7 | Contract changes | Producer class first, then pushed-document observation | done |

<a id="platforms-reported-separately"></a>## Platforms reported separately

- **Rule (in force).** VTI and keyring-wallet are each reported as the original code. Separate runs, rows, columns, pages and numbers per platform. Where: `src/glance/`.
- **A recorded exception that no longer matches a measured surface (in force).** Superseded: material withdrawn from the suite.
- **A defect found in the suite's own harness is fixed in the suite, for every platform (in force).** The adapters' reply filter counts a next step as a reply (SPEC.md 4.4.1) and the document state follows the request's thread (4.12); the keyring-wallet shim registers a DID resolver as a real agent does; the DIDComm adapter counts quiet from the last arrival; the runner signs `auth/step-up/approve-response` for `assertionMethod` as every version of that task requires; the VTA host's bearer carries the authentication factor (`auth/authenticate` 0.1) and the VTC host's seeded actors are members. The original platforms are re-run under the fixed harness and their recorded figures are the re-run's. Where: `src/adapters/keyring-wallet/shim.ts`, `src/adapters/keyring-wallet-didcomm/adapter.ts`, `src/crypto/proof-purpose.ts`, `src/adapters/vti-inprocess/rust/`, `src/adapters/vti/vtc-host/`.

<a id="capture-first-reply"></a>
- **A step captures a value from the first reply that carries it, and the DIDComm adapter waits while only a next step has arrived (in force).** A held task answers with a next step first and the result later on the same thread (SPEC.md 4.4 and 4.4.1), so `capture` reads each pointer from the first reply, in arrival order, where it resolves (a consumer that answers once is read as before), and the keyring-wallet DIDComm adapter keeps waiting, up to the binding's minimum quiet, after the last arrival while every reply so far is a next step. Why: the old reading left `$cap(ibr)` unresolved and reported a slow wallet as a hold with no result, which are harness defects that read as platform failures. Rejected: widening the reply-set rule to accept a next step after the outcome (a stale hold is the wallet's fault). Where: `captureFrom` in `src/runner/engine.ts`, `exchangeStillOpen` in `src/adapters/keyring-wallet/shim.ts`, `test/capture.test.ts`.
<a id="exception-reconciliation"></a>
- **Exceptions are reconciled against the measured results, for the original platform only (in force).** An entry is deleted when its vector passes on the original platform because a vector or the harness was changed for a reason the specification gives (the error reply is a SHOULD, a window the platform does not declare is not enforced, a harness defect), or when the vector is now CLARIFY or SKIP so there is no failure to excuse. An entry whose failure text moved but whose difference remains is rewritten from the real failure (reason, class, `expectFailure`). Why: the entries describe the original code and are the one place a reader learns why a platform differs; an entry that excuses a vector that passes, or text that no longer occurs, is wrong. Rejected: leaving stale entries counted as passes (the exception then reads as a live difference). Where: `exceptions/exceptions.json`, `test/exceptions-file.test.ts` (an entry must match a recorded result of its surface).
- **An exception for a coverage-family vector is advisory (in force).** The coverage vectors (docs/22) are channel `proposed` or `candidate`; the loader and the runner apply an exception to them like any other (keyed on the implementation name and the vector id, channel-blind), and the result is KNOWN-FAIL in the advisory results. Such an entry is outside the headline count of recorded differences (`exceptionsLine`, `src/glance/docs.ts`); the class table on `results/vector-review.md` counts every entry and says how many are for coverage vectors. Until a recorded run folder of the surface holds the result, the entry carries `inherited` (the coverage re-measure of the original platform). Why: the headline must not move when advisory vectors gain entries. Where: `src/glance/docs.ts`; `test/exceptions-file.test.ts`.
- **Which entries went (in force).** keyring-wallet: CTRL-001 to 003, ENV-006 to 009, ERR-004, LIF-003, VRC-PRO-004 to 006, 014, 015, CEX-019, CEX-020 (the missing error reply is a SHOULD advisory, docs/04 section 3.2); CEX-023 and WSH-017 (now CLARIFY). VTI agent service: CEX-001, BND-004, BND-007 (vector over-reads corrected), PP-AUT-015, PP-AUT-149, PP-AUT-211, PP-AUT-261 (harness fixes and the corrected plain vectors), CEX-023 (now CLARIFY). VTI community service: PP-AUT-208, PP-ACL-020, PP-POL-004, 026, 047, and BND-002 (now SKIP: the door reads no bearer token, so no transport identity is offered). The live VTI service entries (BND-002, BND-004, BND-007, PRF-101 to 104, ERR-006, ERR-007, PRF-103) and the witness-server entries were not re-measured in the integrated pass (no container runtime; no witness-server run), so they stand as recorded and are not claimed current.
- **What was rewritten (in force).** keyring-wallet ENV-010 is class A: SPEC.md:756 puts the reply inside the MUST ("MUST reject ... returning `unsupportedVersion` where the transport permits a response"), so a wallet that rejects silently differs from the text; it is not the SHOULD of SPEC.md:1071 (class B was wrong for this vector). VRC-PRO-021 drops the `documentState` line the harness fix removed. DUP-101 to 109 state the observed lines, including the DIDComm v2 limit (the adapter cannot send an anonymous document). TD-001 to 005 no longer assert the pointer line. The issue-leg entries (AUTHZ-001, VRC-ISS-001, 002, 007 to 010, 012, 014 to 016) state the true cause: the verifier names no proof purpose and so demands `assertionMethod` (SPEC.md:373 and :375), not a wrong controller.
- **The shared-connect gate is a spec question, not a vector change and not a wallet change (in force).** VRC-ISS-001, 002, 014, 015 and 016 send a credential proved with `eddsa-jcs-2022`. keyring-wallet can verify it and refuses it while a developer switch (shared connect, off by default) is off. SPEC.md 4.7.1 (line 313) says a conforming consumer MUST be able to verify an `eddsa-jcs-2022` `proof`, which reads as the document's proof; the issue specification (vrc/relationships/issue 0.1, lines 101 and 108) says "a signed credential" and "verifies the credential's own proof" and names no suite. Whether the baseline reaches a credential carried in a payload is Q24 of [the task-force question list](../proposals/tf-question-list.md). The vectors and the wallet's gate stay as they are. Why: the text does not say, and the suite does not decide it by a test.

<a id="owner-open-decisions"></a>Open decisions for the project owner (none taken; each is left as recorded):

- **Interim next step before the terminal reply (runner rule).** The runner now sets aside a `trust-task-next-step` that comes before the terminal reply on the same thread, because SPEC.md names that sequence. Recommendation: keep it (the alternative leaves "got 2 replies" as a vector or engine over-read). Con: it is a reading of the specification by the suite, not a rule stated in it, and it changes what counts as a reply for every platform.
- **VTC Member seeding.** The VTC host now seeds its actors as members, which turned TL-DIR-006 and TL-DIR-008 from FAIL to PASS on the original VTI. That the change is a faithful model of a deployed VTC (not just a way to pass those vectors) has not been verified against a deployment. Recommendation: verify against the VTC's own membership rules before relying on those two results.

<a id="full-coverage-scope"></a>**Full coverage is the scope (in force, decision by the project owner, 2026-11-19).** The suite covers everything in the task force repository (`trustoverip/dtgwg-trust-tasks-tf`), including open pull requests and remote branches. Core tasks were only the first focus; the priority after core is VTI and keyring-wallet, full trust ceremonies end to end matter most, and per-task unit vectors are the finer layer. Non-core families are optional suites a user can choose to run. The `plain task` class in docs/02 is a layer classification, not a coverage exclusion. Private keyring-wallet types with no public specification are held for now. Every task and vector is flagged by spec maturity (the spec `status` field) and by source (main, open pull request, branch). Why: the earlier reading used a classification to leave tasks out, which understated what the suite should measure. Where: [docs/02, classification is not scope](../02-core-trust-task-criteria.md#classification-is-not-scope); the generated matrix `results/coverage/` (`src/coverage/matrix/`, `npm run coverage-matrix`).

<a id="paired-ceremonies"></a>**Paired ceremonies (in force, project owner decision, 2026-11-19).** Whole ceremonies between keyring-wallet and VTI are the most important layer; per-task vectors are the finer one. They are run with the scenario format of docs/25 in runner-carried mode and labelled "ran together, one pair, one carrier, one date" ([docs/26](../26-paired-ceremonies.md)). Choices recorded there: the wallet's own request code is driven through a session the runner carries, so its version step-down is the wallet's; stand-ins (successor key, second phone, card source, the sign-in agent and community DID document) are class D and named; an optional capability `trigger.requireStepUp` and the runner members `continues`, `replay`, `reply`, `$doc:` are additive; scenario differences are kept in the run's issues file, not in `exceptions/exceptions.json`, because that file is keyed on vector runs and its expiry policy; run records live outside the repository.

<a id="signin-ceremony"></a>**Sign-in ceremony (in force, project owner decision, 2026-11-19).** (1) The community refused the starter's request because the `Origin` must equal the configured public URL's origin exactly (request 0.2 service item 3; `portal_origin`), not the loopback address; the adapter now sends the public URL the host reports (or the prebuilt hosts' fixed `http://vtc.test`). (2) A platform sign-in cannot pass the claim while that public URL is http: the VTC checks its own step 1 against the https-only `Origin` schema and answers `internalError`, and the wallet reads only https endpoints. The in-process host source reads `VTC_HOST_PUBLIC_URL` (default unchanged, so every earlier run is measured as before) and the ceremony launcher sets `https://vtc.test`; a rebuilt host is needed and no platform row is called completed before one runs. (3) A reference sign-in service, approver and breakages are the oracle (written from the specification text, not from VTI), so the oracle completes the sign-in end to end; the wallet's own code signs in against it, including its step-down against a legacy-profile service. Two optional capabilities are added (`trigger.serveVersions`, `initiate.oobTamper`); a scenario that needs one is SKIP, classified, for a participant that lacks it. (4) Completion is claimed only at the versions both sides serve: the VTC serves claim 0.2 and prove, grant, respond 0.3, so against it the overlap is the newest of each and no step-down is claimed. (5) Spec-silent, noted and not asserted: whether the respond answer carries a proof (VTI signs it, the wallet requires it, the examples show none) and the shape of `unsupportedVersion` details (VTI and the reference implementation use Type URIs). (6) The first scenario file read a thread its steps never captured (`thread` where the step captured `claim`), so no sign-in could have run; a check that names no thread now reads the thread its step captured.
- **Consent gate against a rebuilt VTA host (D100, run records outside the repository).** The host source now has `/ctl/policy` and `/ctl/enforce`, built with rustc 1.95 (the VTI `rust-version`; no new toolchain was needed). The driver's gated `acl/grant` asked for `capabilities` scope `none`, which the VTA refuses after the gate passes; it now asks for `ceiling`. The runner reads a check, and takes a decision's thread, at a participant from the request that participant was sent (an executor that issues one request per approver files each under its own id).
<a id="gap-families"></a>**Gap families (in force, 2026-11-19).** `vectors/gap` covers every task version that no other vector set referenced: vta, vtc, rooms, did-management, git-ns and messaging (554 versions) and, since 2026-11-20, 148 more in 21 further families (D230 to D237), so every version of the task-force repository has a vector. Rules: a version is a gap task when no vector outside `vectors/gap` names it (the coverage matrix's rule); the specifications are read at one task-force commit through a committed snapshot, with the pinned package as schema source where it ships the version; the vectors are channel `proposed`, non-gating, outside headline counts, and say each spec's maturity (all draft or retired) and source (main, or for the three versions only on pull request 904 channel `pr`; 37 versions of the first step and 6 of the second also differ on a branch and are marked provisional); retired specifications are excluded from runs; a `role` member is a governance token only where the schema accepts any string, and no constraint on a governance role is tested. The first run found no difference on the 29 vectors that reached a platform. The vectors cite the task-force commit they were derived from, not the manifest commit; a full re-pin is the project owner's call. Details: [docs/28](../28-gap-families.md).

- **Reach of the gap versions is read from host declarations and from VTI source, and the two are reported together (in force, 2026-11-19).** The original rows (`vti-upstream-gap-*`) run the prebuilt hosts. They reach 29 of 3,791 run vectors, the four `vta/witness` 0.2 versions: a default-featured host declares nothing more. Where: docs/28, `src/coverage/reach.ts`, `scripts/gap-reach.ts`.
- **Host builds take extra cargo features from `VTI_HOST_FEATURES` (in force).** Needed to reach the 15 `vetting-pcs`/`voting` versions. Not exercised in this change: a build needs crates not in the local cargo cache and a host rebuild was already under way by another agent, so no feature-built host exists yet (work blocker, not firm). `tee` (5 versions) is a further work blocker (AWS crates not cached; attestation answers outside an enclave have not been looked at).
- **Dispatcher constants are resolved per file (in force).** A name two files bind differently is left unresolved rather than guessed. Remaining unresolved: 14 (key signing in the SDK, `vtc` out-of-band sign-in, discovery).
- **No VTI change, no exception, ledger unchanged.** No new vector ran against a platform, so there is no class A to D item to fix.

<a id="onboarding-vetting-ceremonies"></a>**Onboarding and vetting-directory ceremonies (in force, project owner decision, 2026-11-19).** (1) Two groups, `FC-MBR` (17 scenarios) and `FC-IDV` (8), between a wallet and a community, channel `proposed`, advisory and outside every count; run at the versions the platforms serve (manifest 0.4, submit 0.3). The member-onboarding definition cites submit and manifest 0.1: the retired `vtc/join-requests/submit/0.1` stays a documented step of the definition and is claimed by no step here; the reference-only FC-ONB group keeps the definition's shape. (2) The community's administrator and a vetter grant are the community's own out-of-band acts, injected through its `trigger` and signed by its seeded administrator through its door (class D, an operator stand-in); the wallet is never the administrator. (3) The community host runs the boot steps `vtc`'s server start makes and the test-support state omits (shipped default policies, revocation and suspension status lists), selected by `VTC_HOST_BOOT` (the ceremony launcher sets it; every earlier run is measured as before): without them a submission answers `internalError` and an approval admits the applicant but cannot mint the credential. (4) No VTI service handles `vetting/request` (the community answers `unsupportedType`; the types exist only as client wire types): VTI is the community in vetting, so the peer leg stays on the reference scenarios and the platform scenarios cover the community's directory, grant and revocation. The wallet sends only `vetters/profile` of the community leg, so the other tasks are played by the reference member (class D) and the wallet is SKIP (scope) for them through two optional capability names, `initiate.vetterDirectory` and `initiate.foreignPresentation`. (5) The id-less status poll after a rejection is answered `notFound` by the community while the specification reads two ways (a refusal the applicant cannot ask about, against a mapping to the open request): classed unsettled, the scenario accepts `rejected` or `notFound`, a draft question, not filed. (6) A reference community (13 mutants) and member, written from the specification text, are the oracle; the strongest interoperability claim is "ran against both with the same scenarios"; run records are outside the repository.

<a id="persona-rooms-elections-ceremonies"></a>**Persona, directory and elections ceremonies (in force, project owner decision, 2026-11-19).** (1) Three groups, `FC-PER` (5 scenarios), `FC-DIR` (13) and `FC-VOT` (4), between a phone and VTI's agent or community, channel `proposed`, advisory and outside every count (docs/31). Reference oracles and mutants were written from the specification text; each mutant ends its watching scenario failed. (2) Reachability read from source: persona, directory and the elections reads have pairs in code; rooms has pairs in code but its community rooms are disabled on the host (a context at the agent and a room host are needed), so it is not built; the wallet's `voting/ballot/cast` has no VTC handler (a separate ballot-box service serves it, the agent builds it), so a cast is not run and no scenario claims it. (3) Stand-ins, class D: the runner's HTTPS carrier in place of DIDComm (so the persona's key release is refused, which FC-PER-004 records, and the wallet's key borrowing is not run), no hosting server (serverless mint), the second directory member and the administrator, legacy profiles of the oracles for step-down. (4) Class A, FC-PER-003: `vta/contexts/create` 1.0 requires `idConflict` for an existing id; the agent answered `taskFailed`. (5) Class B, FC-VOT-003: an election is included only when the caller may see it and the list declares no error code, so an outsider's list is empty, not refused; the vector and oracle were corrected before platform rows. (6) The three step-down scenarios are SKIP (platform) on the platforms, which serve one version; no "completed" is claimed beyond the overlap. (7) Run records stay outside the repository.


<a id="rooms-ballot-ceremonies"></a>**Rooms and ballot cast ceremonies (in force, project owner decision, 2026-11-19).** (1) Two groups, `FC-RMS` (18 scenarios: the open tier, community leg and agent leg) and `FC-BAL` (14: the ballot box), channel `proposed`, advisory and outside every count (docs/32). (2) The docs/31 "firm" labels were re-measured: the community's rooms were host configuration, not a platform limit (a community started with `VTC_HOST_ROOMS` has them on, with its key holder as VTI's own test double, class D), and the ballot cast is a ballot-box request, hosted by VTI's `vti-voting-service`, which the wallet's own code does send (`postCast`). (3) The rooms group runs the wallet's own ladders, parsers, file sealing and keys tasks; the host-bound requests are signed by the wallet as the persona with the offer's presentation (class D: the agent's act cannot hold the persona's keys over a non-confidential carrier). (4) Corrected as class B before any platform row: FC-RMS-015 (a type outside the act table) and 016 (a named issuer is `issuerNotPrincipal`, not `notAMember`; the act document carries an id and issuedAt). (5) Class A: `rooms/keys/key-package` answered `malformedRequest` where the specification names `notInvited` (FC-RMS-014, and 018 for text that is not a credential). (6) Stated plainly: the VTC host and the agent host were compiled on 2026-11-19; the community leg (FC-RMS-001 to 012) and the ballot box are not run against VTI as results. The community host first needed a second-factor stand-in for the default policy's step-up on `community/create` (`/ctl/stepup`, class D), which is committed but could not be rebuilt because free disk on `/` stayed at 19.7 GiB against the 20 GiB incremental-build rule; the ballot-box host build was stopped by the same guard. No claim about VTI's community rooms or ballot box is made. (7) Run records stay outside the repository.
