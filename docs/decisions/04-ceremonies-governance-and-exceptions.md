# Ceremonies, governance and exceptions

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

Governance in vectors, holds and ceremonies, SKIP classes, exceptions, the keyring-wallet to VTI ceremony set, bindings, interoperability wording, rooms and ballots, wallet driver legs. Part of the [design rationale register](README.md).

## Governance in vectors

<a id="d75"></a>**Decision 75 (in force).** Governance is never determined by conformance tests. Vectors check mechanics against the role set the adapter declares (`governance.roles`, `$role(n)` placeholders) and never assert a built-in role set or default authority. Policy content is gated on `governance.content`; otherwise the vector is SKIP "governance not declared". The one part of governance that gates is the declared essential governance E and whether the platform behaves as declared ([decision 39](#d39)). Where: docs/02 section 5.1; docs/16 section 3; docs/17.

<a id="d77"></a>**Decision 77 (in force; the declaration path is not built).** The suite detects governance that is baked in: differential probes plus a static audit check whether a platform lets the end user declare governance, and report a separate advisory finding, never a ruling on which governance is right. The one GOV-* kind that gates, GOV-DECLARATION-MISMATCH, is not such a finding: it reports that an adapter's declaration of essential governance does not match the platform's behaviour ([decision 39](#d39)). Where: docs/17; `docs/proposals/governance-baked-in-audit.md`.

<a id="d74"></a>**Decision 74 (in force).** Access control (`acl/*`) goes into 2L-1, paired with governance declared through the `understanding` family (open pull request #904). See [RD4](05-application-profiles-roadmap.md#roadmap-decisions-rd1-to-rd7).

<a id="d39"></a>**Decision 39 (in force).** Essential versus extended governance, and the ceremony family split by it. **Tier E, essential governance, gates:** the platform's authority set (the principals who may decide a held task) and `minApprovals` (at least 1), declared by the adapter in `capabilities.governance.essential` (the shape of `GovernanceDeclaration`: `principals` plus `consent`) from the platform's own configuration, from the configuration the harness gave it for the run, or from a fixed built-in rule, and recorded in run.json. The suite never asserts what E should be; a fixed built-in rule still fills E and is the advisory GOV-FIXED, not SKIP; a declared set of one is labelled single-party. **Tier X, extended governance** (role names and hierarchy, delegation, step-up policy, `sealBeforeGrant`, `termsRef`, authority source, provisioning, content) is advisory GOV-* only. **The ceremony family is split three ways:** (1) `registry`, gating only what the framework states for any held task: the next-step hold and its resubmission (CER-001, 002, 015), duplicate absorption (CER-005), 2PC-006 and 2PC-007; (2) behaviour relative to the declared E, written "behaves per declared E" so it runs at k = 1 too (CER-017 completion exactly at the k-th distinct approval, CER-018 an outsider's approval refused, CER-019 a repeat not counted twice), `candidate` because the ceremony family has no Trust Tasks home; SKIP only for "authority set of one" or "declared minApprovals of one" where a vector needs an approval before the deciding one, and "authority set unreadable" with GOV-NOT-PROBED; (3) the suite's own ceremony design (the seven-day deadline, `deadlineLapsed`, abort as non-retryable `taskFailed`, the closed `details.reason` vocabulary, a quorum of every named administrator, reset rules, verbatim retention, the status query, `proposerApproves`), channel `proposed`, profile `ceremony-design`, advisory (CER-003, 004, 006 to 014, 016, 2PC-001 to 005, 008, TIME-103). **Adapter honesty check:** the harness probes the declared E in every suite run (completion at the declared k; an approval from a principal outside the set not counted); a mismatch is the finding GOV-DECLARATION-MISMATCH, the only gating GOV-* kind, which turns every result that rests on E into FAIL and the exit code non-zero; lying reference variants show that the check catches what it claims. `proposerApproves` stays a declared adapter property; `verifyReceipt` stays an optional capability; framework cells measured through the fixture carrier stay labelled as such. Why: decisions 75, 77 and 79 (no test decides governance; what rests on suite-local text does not gate), while a held task still needs to know who decides it. Where: docs/02 section 5.1; docs/04 sections 11.4, 12 and 19.1; docs/17 section 2.1; `src/runner/essential.ts`, `src/runner/honesty.ts`, `ceremonyChannel` in `scripts/generate-vectors.ts`; `test/essential.test.ts`, `test/honesty.test.ts`. Not yet exercised: no VTI or keyring-wallet adapter offers ceremonies, so the honesty check is not run for them.

## SKIP classes and gating

- A group that needs a capability is gated by it (`requires`, `skipIfOptional`), so a platform that does not offer it gets SKIP with a reason, never a FAIL. The relationship-credential groups are SKIP for VTI on that basis.
- <a id="d42"></a>**Decision 42 (in force):** a peer without a settable clock declares `clockFree` and runs in rebase mode; vectors that need clock control are SKIP for it with the reason. Exactly one of `clock` and `clockFree` must be declared. A matrix cell is green only when at least one of its anchor vectors passes and none fails (the vacuous-pass rule). Every result records the pinned kit and VTI ref. Runner-mediated pairs record their bytes.
- A SKIP is classed from its reason by `results/skip-classes.json`: *not-applicable* (the platform does not implement it), *not-reached* (the setup cannot drive it yet; the reason must name the specific, checked limit, never only that the adapter lacks a capability), *version-mismatch*, and *out-of-tier* (not counted). A reason that matches no rule is reported as unclassified so that it gets one.
- A platform that does not offer a task declares it in `notOffered`, so the SKIP says "not offered by the implementation".
- <a id="cited-not-offered"></a>A SKIP is *not-applicable* only from a cited `notOffered` entry (`{ reason, evidence }`: the platform source and ref, or the observation). The runner records the evidence on the SKIP and marks every results block `notApplicableRule: "cited-notOffered"`; on such a block a rule in `results/skip-classes.json` that would give not-applicable gives not-reached unless the SKIP carries evidence. Blocks recorded before the rule keep their class. Why: "the adapter did not declare it" is not a platform fact (standing constraint). Where: `gateDecision` in `src/runner/suite.ts`, `cited` in `src/adapter/contract.ts`, `skipClassOf` in `src/glance/model.ts`; [docs/04 section 8](../04-suite-design.md#8-outcomes-capability-gating-and-known-failures-built).
- <a id="excluded-by-tier"></a>A vector outside the selected tier is recorded under `excludedByTier` in results.json, never as SKIP: SKIP is reach, and a Tier 2 vector in a Tier 1 run says nothing about reach. The matrix and the at-a-glance pages show the count apart; older runs (tier SKIP reasons) are read as the same thing. Where: `isTierExclusion` in `src/runner/suite.ts`, `src/runner/matrix.ts`, `TIER_SKIP` in `src/glance/model.ts`; [docs/04 section 8](../04-suite-design.md#8-outcomes-capability-gating-and-known-failures-built).

- <a id="min-quiet"></a>A verdict that rests on no reply (`silence`, `any-refusal`, `duplicate` with an empty reply set) needs the adapter to report at least the run's minimum quiet period: 0 ms over `in-process` or `https`, 1500 ms over DIDComm or an unknown binding, or `--min-quiet-ms`. Less, or no number, is FAIL `QUIET-NOT-ESTABLISHED`, never a pass; the engine does not wait and ask again, because a later reply is not attributable to the step. SuiteRun and run.json record `quietPeriod`. Why: a slow reply over an asynchronous carrier would otherwise read as silence. Rejected: waiting in the engine (it cannot see a late reply), recording the step as SKIP (it ran; the adapter's answer is what is short). Where: `src/runner/quiet.ts`, `runVector` in `src/runner/engine.ts`; [docs/04 section 3.3](../04-suite-design.md#33-verdicts-that-rest-on-no-reply-the-minimum-quiet-period).

## Exceptions (KNOWN-FAIL)

- Exceptions live in `exceptions/exceptions.json`, one entry per implementation (or platform) and vector, with a mandatory `owner`, an `expires` date and a reference. An expired exception fails the run; so does a stale one (the vector now passes).
- <a id="expiry-policy"></a>While no outward contact is allowed, the owner is `unassigned`. Expiry dates are set in one place, `exceptions/expiry-policy.json`: an anchor date plus a whole-day offset per implementation key, so the surfaces expire on different days. The anchor is a placeholder until a review date with the task force is set. Why: one shared date makes every entry expire at once, a mass renewal with no review. Rejected: hand-set dates per entry (drift, no single place to move them). Where: `src/vectors/expiry-policy.ts`, `scripts/expiry-policy.ts` (run by `npm run regen`, checked by `npm run check:docs`), `test/exceptions-file.test.ts`. Per-implementer expectation files are future work ([challenges.md section 8](../challenges.md#8-future-work)).
- Each entry is classed by what it shows; the classes are defined in [results/vector-review.md](../../results/vector-review.md).
- <a id="challenges"></a>An implementer disputes a vector through a written challenge ([challenges.md](../challenges.md)): grounds `spec-silent`, `spec-inconsistent` or `vector-overreads`, quoted evidence, and one recorded outcome (vector fixed, retired, moved to CLARIFY or candidate, or challenge rejected with the text that decides it). While it is open the result is a KNOWN-FAIL whose expiry is the deadline for an answer. Challenges are local files until the project owner opens a channel. Why: the people a vector measures need a written way to dispute it. Rejected: deciding disputes informally (no record of why a vector stands).
- Each entry records whether the platform's implementer has acknowledged it (`acknowledged`: `null` or `{ by, on, ref }`); a null entry is shown as unacknowledged in KNOWN-FAIL reasons and in the vector-review totals. Where: `src/vectors/load.ts`, `src/runner/suite.ts`, `src/glance/docs.ts`.
- <a id="platform-surfaces"></a>An exception keyed on a platform applies to every row whose capabilities declare that `platform`; every surface of a platform that measures the platform's own code declares it. The keyring-wallet DIDComm rows (v1 and v2) both declare `platform: keyring-wallet`, so the wallet's exceptions apply to each, a stale entry fails on the row that no longer meets it, and a recorded run of either row gates keyring-wallet (the at-a-glance generator refuses a measurement recorded with a platform as a not-gating experimental note). Why: a row outside the mapping shows each recorded difference as an unexplained FAIL and hides stale entries. Rejected: an advisory folder for v2 (it would never be measured on the same footing). Where: `src/adapters/keyring-wallet-didcomm/adapter.ts`, `src/runner/suite.ts`, `recordedPlatform` in `src/glance/model.ts`; [docs/18](../18-keyring-wallet-over-didcomm.md), [docs/15](../15-keyring-wallet-didcomm-v2.md#how-the-suite-measures-the-v2-row).
- <a id="exception-surfaces"></a>Exceptions are keyed per measured surface: the in-process VTC host has its own implementation name (`verifiable-trust-infrastructure-vtc-inprocess`), distinct from the live service. Each entry is justified by a recorded KNOWN-FAIL or FAIL of its surface or carries `inherited`, and states the failure it excuses in `expectFailure` (patterns over the engine's failure lines); a failure that does not match is FAIL. The review class is the structured `class` field, set only where the reason text supports it. An entry keyed on a platform names in `notOn` (with a reason) any row of that platform whose path does not carry the difference, and that row is judged without it. Why: a pooled key applied the host's entries to the live row (whose stale ones could never be detected), an entry with no failure signature hid a vector that started failing for another reason, and a platform entry over a difference one carriage does not have would read as stale there for good. Where: `src/runner/suite.ts` (`unmatchedExpectations`), `src/vectors/load.ts`, `src/adapters/vti/adapter.ts` (`VTC_HOST_NAME`), `test/exceptions-file.test.ts`; [docs/04 section 8](../04-suite-design.md#8-outcomes-capability-gating-and-known-failures-built).

## KW-to-VTI ceremony set (FC-KVC, FC-KVX)

- <a id="kv-scope"></a>Both groups are channel `proposed`, non-gating, outside every headline count and the catalog total; evidence kind `complete-ceremony`, never a PASS ([27](../27-kw-vti-ceremonies.md)). Run records stay outside this repository; pages cite run names only.
- <a id="kv-roles"></a>A scenario names roles, never governance. ## Interoperability wording

- VTI's row is "framework behaviour over HTTPS", never "VTI conforms". keyring-wallet over the shim is "logic over a shim carrier", never wire interop.
- The suite measures conformance platform by platform. Conformance-implied agreement is recorded in the pair matrix; demonstrated interoperation (a recorded exchange) has not been recorded. The exact wording is the rule in [docs/14 section 5](../14-interoperability-tracking.md#5-wording-for-docs12-and-the-artifact).
- <a id="artifact-crossed"></a>**Artifact-crossed is its own evidence kind (in force).** Documents one platform emitted, relayed by the runner into another platform's receiver adapter, are recorded as `artifact-crossed` with the receiver's verdict and no oracle; never called demonstrated, never summed with conformance counts, never a pair-matrix figure or ledger entry. Why: relayed bytes skip carriage, sessions and discovery, so they are stronger than conformance-implied and weaker than a live exchange. Rejected: ledger entries with carrier `other` and a "runner-relayed" note (would sit beside demonstrated entries and read as one). Where: [docs/14 section 7](../14-interoperability-tracking.md#7-artifact-crossed-evidence-runner-relayed-documents); `src/crossed/`; `test/crossed.test.ts`.
- <a id="independent-implementations"></a>**Independent implementations are counted per group, without the reference (in force).** A generated report counts, per vector group, the platforms independent of the suite that passed it (some PASS, no FAIL or KNOWN-FAIL) in recorded runs, each labelled with its run folder and suite version and "earlier recording" where it is. The reference adapter is shown apart and never counted; the truststackers original is reported as not reachable. Why: maturity of a specification feature needs implementations that did not grow up with the vectors. Rejected: per-surface counts (one platform would count several times). Where: [docs/14 section 8](../14-interoperability-tracking.md#8-independent-passing-implementations-per-vector-group); `src/glance/independent.ts`; `results/independent-implementations.md`; `test/independent.test.ts`.
- VTI is one platform with two measured surfaces (the live community service over HTTPS and the agent handlers in process). The surfaces are never summed or ranked.

<a id="claims"></a>**Claims use a template and no status words (in force).** A result is stated with the template in [claims.md](../claims.md): platform and commit, surface, suite version and commit, run folder, tier, channel, reach, and every count with KNOWN-FAIL ids cited as `<version>/<id>`. The status words listed in claims.md are not used unless the run is at a released (not pre-release) suite version with FAIL 0 and KNOWN-FAIL 0; no released version exists, so they are not used at all. Why: a draft suite's results must not be read as a status award. Rejected: a path to a status award (the suite is a draft, unadopted). Where: `src/glance/claims-lint.ts`, `scripts/lint-claims.ts`, `test/claims-lint.test.ts` (run by `npm test` and `npm run check:docs`).

Run records stay outside the repository; the pages cite run names (`rms-vti-*`, `bal-vti-*`, with the corrected first passes kept as `*-pass*`). - <a id="d207"></a>**Hosts built (D207).** The VTC host with `/ctl/stepup` (suite `c9b5d6d`) was rebuilt incrementally, then the agent host and the ballot-box host (first compile, no source error) against the local VTI checkout, with `cargo +1.95.0`, `nice -n 10`, memory and load checked before each build, and 23 GiB or more free on `/` throughout. - <a id="d208"></a>**FC-RMS-006, class A (D208).** `rooms/records/put` 0.3: the payload schema says `expectedVersion` `0` is create-only and fails if the key exists, and that on mismatch the host returns `rooms/records/put:versionConflict` carrying the current version; VTI answered the generic `taskFailed` (conflict). - <a id="d209"></a>**FC-RMS-004 and the ballot vectors, class B (D209).** The reference member's blob begin had a chunk size under the schema's 16384 minimum and no transfer mode (`uploadKey`): fixed in the suite (the oracle now enforces the bounds). `cast:leaf:<n>` assumed the first cast is board index 0; the board holds lifecycle entries first and the task fixes only "the board index", so the check is now relative to the first receipt kept. The `wrongDigest` variant was not a multihash; it is now a well-formed digest of another manifest. None of these is a platform difference; no VTI change.
- <a id="d210"></a>**FC-RMS-005 and the ballot hosts, class D (D210).** The VTI adapter counts a write once per distinct reply id (a redelivered document is answered with the same reply). The ballot host's cast carries the host's community, its `counted` observation reads the schema's `replaced` entry kind, and the cast-source callers send `Content-Type: application/json`. Stand-ins and harness defects only.
- <a id="d211"></a>**Outcomes (D211).** Community leg, FC-RMS-001 to 012, reference member, original wallet: 5 completed, 6 ended as specified, 0 failed, 1 skipped (012, platform: no `trigger.serveVersions`). The wallet row agrees with the reference member on every scenario; no difference between VTI's ballot box and the specification text was found.
- <a id="d212"></a>**Generated table (D212).** The rows (`rms.ref`, `rms.up`, `bal.ref`, `bal.up`) are in `results/ceremony-rows.json` and the generated ceremony table (regen against a copy of the final-suite results with these records added); the "built, not run" statements in STATUS, results/README and docs/32 now state the recorded outcomes. ## VTI-KW wallet driver legs

Nothing was pushed, filed or sent. Run records stay outside the repository (`onb.legs.up.vti-up`).

- <a id="d600"></a>**FC-ONB-004 and 006: the wallet holds a membership it was delivered, and acknowledges it (D600, 2026-11-21, class D).** The wallet host now declares `initiate.reciprocate` and has a `join-vmc` kind: the wallet's own `reciprocateIfOwed` (it owes an acknowledgement only for a membership it holds; its own VMC builder and sender) over an in-memory community store. The membership comes the way the wallet's persona inbox gets it: the community's pushed `credential-exchange/issue` delivery goes to the wallet's own `receiveIssue` (the card check is the wallet's time and proof checks without the status-list read, which the harness does not host). FC-ONB-004 gains a `deliver` step (`relayPushed` V to K, new field `ifOffered`: a sender without `observe.pushed`, as the oracle community, hands out nothing and the step does nothing; a sender that offers it and pushed nothing still fails it). `join-vmc` with `unsolicited` (FC-ONB-006, a delivery before approval): the wallet never does this, so the driver builds the acknowledgement of a stand-in grant with the wallet's own builder, signs and sends it with the wallet's own sender and the request id.
- <a id="d601"></a>**The VTI adapter serves `solicit` and `observe stored vmc` (D601, 2026-11-21, class D).** FC-ONB-004's community seat needed the administrator's `vtc/members/solicit-vmc/0.1` (door call, answer recorded as `admin:solicit:<code>`) and a count of the acknowledgements the community holds (`vtc/members/credentials/0.1` per member, `memberVmc` present). Both were missing, so the earlier row skipped before it reached them.
- <a id="d602"></a>**Pin result: FC-ONB-006 ended as specified; FC-ONB-004 fails on the pin at solicit-vmc (D602, 2026-11-21, class A candidate).** Row `onb.legs.up.vti-up` (pin host 26d0da81 with seeded defaults, rooms ceremony mode, original wallet): FC-ONB-006 ended as specified (refused, `vtc/members/vmc:requestNotApproved`, nothing stored); FC-ONB-004 reached the wallet delivery (two issue documents handed to the wallet) and then the pin answered `solicit-vmc` 0.1 for an active member with `internalError` (HTTP 500, "the request itself was accepted"). vtc-service `request_vmc` pushes the request with `Thread::Root(<bare uuid>)`, so the document id is not a `urn:uuid:` (the credential deliveries use `Thread::New`); that is a suspect, not confirmed (the host's log is silent; a tracing build is needed). Class A on the VTC unless the trace shows otherwise; the wallet leg after it is not reached.
- <a id="d603"></a>**FC-CEX-002: the wallet's missing verifier pre-trust is a wallet gap, not a driver gap (D603, 2026-11-21, class A on the wallet).** credential-exchange/query 0.1 (spec.md "Answer, defer, or refuse"): a pre-trusted verifier is auto-consented and answered with `present`; any other verifier is deferred and decided out of band. The spec does not require a holder to keep a pre-trust list, so the wallet's default (every matched query waits for its person) is a policy the spec allows, but the scenario's auto-consent leg needs the holder to hold one and the wallet has none (`optional:trigger.verifierTrust` is not offered; shim.ts cites the wallet's `respondToCredentialExchangeQuery` as the only path to a presentation).
