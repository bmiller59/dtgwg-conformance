# Vector completeness (vectors/complete)

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

The completion set closes one measured gap: for the latest version of each task that VTI serves or the keyring-wallet source gives a role with code, a positive vector (a valid request answered, or a document emitted). Every task specification involved is draft; each vector says so in its `source.note`.

## Scope and measure

- `vectors-src/complete/scope.json` lists the in-scope tasks with the evidence (VTI served, wallet role) and the revisions read (task force, VTI, keyring-wallet): 682 tasks, the latest version of each (data of the 2026-11-22 third pass: 636, plus 29 served through a typed dispatcher or an HTTPS route (R-03), plus the 17 voting-service tasks of the routing table `const SERVED` in `vti-voting-service/src/dispatch.rs`, read by `uriMacroTable` in `src/coverage/matrix/vti.ts` (S-02); `voting/ballot/cast` 0.1 gains the `voting` surface). The scope rule (D742): a task is in scope when it is the latest version of a task-force task and VTI serves it (dispatch table, `on!` registration, typed dispatcher, HTTPS route) or keyring-wallet has a role with code for it (emits, serves, names-only); a task VTI only names or produces, with no keyring-wallet role, is not exchanged between the two and is recorded in `outOfScope` with its VTI and KW roles (61 entries, among them consent/approve-request, push/wake, push/provision, the VTC notices; the rule is dispatched requests only: a document VTI only produces, or only verifies as embedded evidence or receives as a client, is out of scope, with the reason naming what VTI does with it, S-05). Entries added after the first pass say why (`note`; `vtiServedVersion` or `kwNamedVersion` where the platform exchanges an older version than the latest, recorded as "VTI behind latest" or "KW behind latest"), and `outOfScope` lists the slugs left out, each with the reason (retired as latest, not exchanged between VTI and KW, no task-force specification). `scripts/scope-add-served.ts` adds the tasks the fixed scanner (`typedDispatch`, `ttRoutes` in `src/coverage/matrix/vti.ts`) finds served and records the rest. `node scripts/vector-completeness.ts scope <coverage-matrix dir> <out>` rebuilds the derived part from a `npm run coverage-matrix` run.
- `node scripts/vector-completeness.ts report vectors-src/complete/scope.json results/coverage/matrix.json` prints the measure, each figure with its denominator: tasks covered by at least one vector, with a positive vector, with a positive vector that **asserts success**, with a **weak-only** positive, with a negative vector, with both, with a gating vector, and per family, and the share of tasks whose positive (or negative) vectors are **all skipped for safety by default** (covered, but not run without a disposable deployment; R-07); wallet-emitted tasks with an emit vector; ceremony step task types with both polarities (the ceremony figures read the committed matrix named on the command line). Polarity is read from the dispositions the steps expect and credited to the Type URI each step sends or emits (R-02): a seeding step (`rooms/create` expecting a response, ahead of negatives for `rooms/epoch/mint`) credits `rooms/create`, not the probed task; a step that names no Type URI (a template step) credits the Type URIs its vector names; the edge figure is a title heuristic and is labelled so. Only the vector files a set's manifest lists are counted, and a retired or excluded vector gives no coverage: the runner never runs them. The code is `src/coverage/completeness.ts`, tested in `test/complete.test.ts`.
- Asserted and weak positives are two numbers and never one. A positive vector is **asserted** when a step expects the task's own response (or an emitted document) and **weak** when its positives are only `answered` without `success` (any non-envelope answer passes). Maturity of every specification involved: draft.

## What is generated

`scripts/generate-complete.ts` writes `vectors/complete/` (group `VC-<FAMILY>`, `VC-EMIT`). For each scope task it writes what its own text supports, reading the facts in `vectors-src/complete/task-facts.json` (effect, codes the text names, a "no response is not a failure" clause; rebuilt by `scripts/derive-task-facts.ts` from the task-force text):

- the shared mechanics vector of `src/plain/build.ts` (a schema-valid, signed, addressed request, SPEC.md 7.2 rules 1-13, 4.4.1, 7.1 item 3), in the **asserted** form where the task defines a response and neither state nor a free-form value decides it (read-only, the request names no identifier or free text, the response is buildable, and none of the task's front-matter `errorCodes` is reachable for the request: R-01). A code is not reachable when it is a standing code covered by `optional:authorised` (`notAdministrator`, `notMember`, `notAMember`: the capability means administrator and membership standing as well as permission, R-06; and a witness's own policy for `witness/session:refused`, S-01), or needs a request member the vector does not send (a cursor code with no cursor, `invalidWindow` without `since`); a code such as `streamUnavailable`, `notFound` on a transport kind, `noKeyHolder` or the default-range `invalidRange` of `vtc/rooms/usage` is reachable, so that task is weak (VC-VTC-006, VC-VTA-040, VC-VTC-033, VC-VTC-124). The same rule holds for every set, not only this one (S-01): `src/coverage/reachable.ts` audits every step of every vector that expects a task's own response (`response`, or `answered` with `success`), and `test/fixes3.test.ts` fails when a task's front-matter code can fire for the request and the step neither accepts it (`orRefusal`, `acceptCodes`), nor is covered by `optional:authorised`, nor cannot arise (a member the request does not send, a minted id). The coverage vectors accept a task's own standing codes (for example `git-ns/account/list:notCommunityAdministrator`) beside `malformedRequest` and `permissionDenied`, and a clamped-`limit` response step also accepts the codes the request can draw (`vtc/relationships/list:notFound`); the witness vectors require `optional:authorised`; the seeded probes mint ids with `$mint(name)` (a short lowercase token per run salt, usable inside a longer string) so a second run does not meet `alreadyBound` or `alreadyExists`. A stream's follow-on documents (`expect.followOn`) are noted, not a second answer: the one reply must be the task's own `#response`, valid against its schema; the vector requires `optional:authorised`. Every other positive is the **weak** form (title and cite say why);
- the specification's own valid request examples (up to three), always weak, and none for a destructive task (its example identifiers are not sent, F-06). A create-type payload carries a suite-minted id in place of a fixed one;
- a negative vector for a task that has none, from its required members, closed payload, wrong-type member or the invalid examples its specification ships (SPEC.md 7.2 item 2, 8.3);
- for a task the wallet emits with no emit vector, the producer-class vector (SPEC.md 7.1 items 1-3, 7.3 item 17).

The reference oracle answers with the extended schema builder (the one used for request payloads), so only a response schema no builder can satisfy (`vta/credentials/issue/0.2`: allOf with unevaluatedProperties) is listed in `vectors/complete/not-generated.json`, with the tasks that have no negative (emit-only, no receiving side) and the destructive tasks whose examples are withheld. The test "is exactly what scripts/generate-complete.ts produces" compares every file in the directory, so an unlisted file fails it.

## Answered, silence and codes

`answered` (docs/04 section 11.7) accepts a response, a next step, or an error whose code is not an envelope code. Silence is an advisory, never a failure (SPEC.md 7.2 closing paragraph, section 8; authorisation is the consumer's, 7.2 item 10), and `vta/management/reload-services/1.0` says plainly that a dropped connection is not a failure. `internalError` is an advisory. A code is accepted through `expect.acceptCodes` only where the task's text states an explicit consumer rule for it (R-04: a sentence with MUST or SHOULD, a refusal verb and the code, or an arrow to it in a MUST item; `proofInvalid` only for a check against live state), not where a sentence merely mentions it (a missing-proof clause, a producer rule, a reader's fallback, a table row), and only where the vector can create the situation the text names (S-04). The two clauses that fit the second rule, `idConflict` of vta/webvh/servers/register (an id already in use: the vector sends a suite-minted id) and `proofInvalid` of vtc/install/claim/finish (a live-state check behind an unknown-`claimId` refusal: the vector's `claimId` was never issued), cannot arise for their vectors' payloads, so VC-VTA-056 and VC-VTC-073 accept no code and cite why ("Not accepted (S-04)"); no vector carries `acceptCodes` now. `acceptCodes` is honoured under `success` as well (task codes match by their local name). `expect.success` (asserted form) fails on anything else but the task's own response. For a task that declares no response, a follow-on task document is observed and neither accepted nor refused as a reply: whether that is a reply under SPEC.md 4.4.1's three dispositions is spec-open (class C, recorded, not filed).

## Effect and safety

Every vector that sends to the implementation carries `effect` (`read-only`, `mutating`, `destructive`), read from the task's `sideEffects.level` (a task that states none counts as mutating). The runner does not run a `mutating` or `destructive` vector unless the run names a disposable deployment (`--allow-effects <name>` or CONFORMANCE_DISPOSABLE_DEPLOYMENT): it is reported `SKIPPED-SAFETY`, apart from PASS, FAIL and SKIP, in no count and not in the exit code. An untagged vector (the older sets, about 9,000) takes the effect of the tasks it sends to from `vectors-src/task-effects.json` (every task version at the pinned task-force commit; `scripts/derive-task-effects.ts`): a destructive task is never sent to without the opt-in, a mutating task is not sent a request that may succeed (a step expecting a positive disposition); a step with no Type URI is not judged. The command line applies this to every set (R-05); library `runSuite` keeps the tags-only default unless it passes `deriveEffects: true` (S-06): about 80 call sites run every set against the in-process reference oracle, which is never a deployment, and must run the mutating and destructive vectors; the only path to a real deployment is the command line, which always derives, and a library caller that drives a deployment passes the option itself (documented at the option in `src/runner/suite.ts`, tested in `test/fixes3.test.ts`). A template step (no Type URI: `$carrier`, the ceremony and witness templates) is not judged, so a vector whose only sends are template steps keeps its tag; a negative step to a mutating task is not gated. Negatives on mutating tasks that carry a tag in this set are skipped too, and count as covered (R-07), which is why the measure reports the skipped-by-default share apart. Destructive mechanics vectors behind the opt-in still send builder values (for example `did:web:alice.example`, an empty `vtc/config/import` document); that is acceptable only on a named disposable deployment.

## Channel

Every vector is channel `proposed`, profile `vectors-complete`: advisory, outside the gating set. Promotion follows docs/33 (recorded runs of the vector, then the batch edit in `vectors-src/promotions.json`); none is promoted here.

## What the reachable-code audit looks at (F3-01 to F3-04, D889)

`auditCoverage` (`src/coverage/reachable.ts`) reports, per set, the vectors loaded, the steps that assert a task's own response (`response`, or `answered` with `success`), how many of them send a template, and how many name a task whose front-matter codes are known. Template steps are audited: the template's own document is read (`templateDocument`, `src/runner/build.ts`) with the step's `params` laid over it; its `mutate` list is not applied (a limit, tested). The hand-written ceremony and consent flows that templates drive carry thirteen recorded exemptions (`TEMPLATE_EXEMPT`: a participant's own decision such as `declined`, and preconditions the earlier steps build); the test fails when an exemption stops matching a step, so the list cannot grow stale, and it is a recorded limit, not a closed finding. A guard test fails when a set directory drops out of the audit, when `answered` with `success` steps are ignored, or when an asserting step names a task or template of an unknown kind. The 105 seed steps with a fixed identifier (create, bind, register outside the probes) are all weak (`answered` without success, or `orRefusal`), so none can fail a second run; the test keeps it so.
