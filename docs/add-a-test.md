# Add or fix a test

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

The suite has two kinds of test: **vectors** (one task, one implementation, a verdict) and **ceremony scenarios** (several tasks between named roles, reported as completion, never conformance). This page walks through adding a vector end to end, then points to the full recipes. Every task specification involved is draft. Work from a git clone: the page checks read the list of tracked files from git.

## Before you write: is it new, and is it in the text?

- **Find the vectors that already cite the text.** Each vector names the specification file it rests on in `source.tfRef.repoPath`. For example, for the propose task:

  ```sh
  grep -rl '"repoPath": "specs/vrc/relationships/propose/0.1' vectors/
  ```

  [results/traceability.md](../results/traceability.md) lists, statement by statement, which normative sentences are cited by a vector and which are not.
- **Quote the sentence.** A vector rests on a sentence of a specification. If the text is silent or open, the right contribution is a specification question (an issue from the template), not a vector that picks a side.
- **A vector you think is wrong** is fixed the same way it is added: in its generator. If the fix is that the vector reads more than the text says, it becomes CLARIFY ([CONTRIBUTING.md, recipe 4](../CONTRIBUTING.md#4-add-or-triage-a-difference-known-fail)); if you are not its author, you can also [challenge it](challenges.md).

## Walk-through: add a vector

This adds a trivial positive vector to the envelope group (`ENV`) of the core family. Do the same with real content in the generator of the family you need.

1. **Find the generator.** Files under `vectors/` are generated and never edited by hand. The table of families and generators is in [CONTRIBUTING.md, recipe 3](../CONTRIBUTING.md#3-add-a-vector). The core family is `scripts/generate-vectors.ts`.
2. **Add the vector** with the next free id of its group (ids are never reused; `vectors-src/id-ledger.json` lists every id ever issued). In `scripts/generate-vectors.ts`, inside the `ENV` file after `ENV-014`:

   ```ts
   v("ENV-015", "a minimal valid carrier request is answered", 1, ["framework 4.1 to 4.4", "SPEC.md:1011-1023 (7.2)"], [ok()],
     { mutants: [] }),
   ```

   The arguments are the id, a title, the tier (1: the framework's own requirements), the specification text it rests on, and the steps: here one step that sends a valid request and expects a response. A negative vector also names in `mutants` the deliberately broken reference adapters it must catch ([docs/04 section 9](04-suite-design.md#9-non-vacuity-built)).
3. **Regenerate** every generated file, including the id ledger (about 15 seconds):

   ```sh
   nice -n 10 npm run regen
   ```

4. **Run it against the reference adapter.** The PASS count goes up by one, and `results-local/new-vector/results.json` has a row for `ENV-015`:

   ```sh
   nice -n 10 npm run suite -- --adapter reference --tier 1 --allow-effects reference-in-process --out results-local/new-vector
   ```

   A structural mistake (a missing citation, an unknown expectation, an id of another group) stops the run before anything is sent, with `vector load failed:` and the place of the problem, for example `framework/env.json: $.vectors[14].spec: non-empty array of strings (traceability) required`.
5. **Check it.** The quick check takes seconds; the full check is what a pull request needs:

   ```sh
   nice -n 10 node --experimental-strip-types --disable-warning=ExperimentalWarning --test test/vector-ids.test.ts test/vectors.test.ts
   nice -n 10 npm run check:docs
   nice -n 10 npm test
   ```

   If you skip step 3, the id test says `ENV-015 is not in vectors-src/id-ledger.json: run npm run regen`.

Before you propose it, set the channel and tier honestly: a new vector starts advisory, and only a vector citing a specification in the Trust Tasks repository can ever gate. The points a reviewer checks first are in [how to contribute](community/contributing.md#add-a-vector); the full recipe, including channels, `requires` entries and retiring a vector, is [CONTRIBUTING.md, recipe 3](../CONTRIBUTING.md#3-add-a-vector).

## Add a ceremony scenario

Ceremony scenarios are generated by `scripts/generate-ceremony-scenarios.ts` and its group sections, and proved first with two reference parties:

```sh
nice -n 10 npm run ceremony -- --participant P=reference --participant R=reference-peer --scenario <id>
```

The steps, and the rule that a deliberate fault must end the scenario in `failed`, are in [how to contribute](community/contributing.md#add-a-ceremony-scenario). Scenario design is in [docs/25](25-ceremony-scenarios.md).

## Propose it

One change per pull request, with the generated files regenerated and committed, and each commit signed off (`git commit -s`, the Developer Certificate of Origin). The pull request template in `.github/` lists what a reviewer checks.
