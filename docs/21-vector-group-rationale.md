# Vector group rationale: why the groups and the contract are built as they are

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

[04-suite-design.md](04-suite-design.md) says what each vector group and contract member is. This page says why: the choice made, the reason, and the alternative rejected where one was considered. Project-wide rules are in [decisions](decisions/README.md). The vector files are authoritative for ids and counts.

## 1. Tier 1 audit: where vectors sit

The audit ([decision 47](decisions/02-specs-tiers-and-channels.md#d47)) classes every Tier 1 vector by its grounding and moves anything that is not a framework MUST.

- **Tier 2 sub-groups.** `profile-window`: TIME-001 to 011, 015, 017 to 020 and DUP-110 to 113 (fixture rows at the profile pins). `attested`: TIME-012, TIME-016 (no skew at the expiry edge, which a consumer may add), TIME-021 (the refusal rests on the carrier requiring `issuedAt`) and BND-007 (the HTTPS status table; BND-004 keeps the Content-Type MUST and the 200 case). `profile-witness-share`: WSH-001 to 005, 013, 017, 025. `profile-ceremony`: 2PC-001, 004, 005, CER-003, 008, 009, 014 and TIME-103 (a ceremony window is policy); like the rest of the suite's ceremony design they are also channel `proposed`, profile `ceremony-design`, so advisory ([decision 39](decisions/04-ceremonies-governance-and-exceptions.md#d39)). `profile-p384`: PRF-003 and PRF-005, behind capability `cryptosuite:ecdsa-jcs-2019:P-384` (P-384 is not in the framework text).
- **CLARIFY.** PRF-108, VRC-PRO-011 (an unsigned request accepted; consistent with DIS-015), LIF-001, LIF-002, ERR-002, CER-011, VRC-PRO-009, VRC-PRO-010, RSP-002, and DUP-009 and DUP-010 (the scenarios are real and VTI differs, so they are kept rather than deleted).
- **Relaxed engine assertions.** Thread and party mismatches are advisory (a next-step thread mismatch still fails). `inResponseTo` is advisory except where a vector is about retained errors. A duplicate passes if it is silent or an equivalent `#response`. `retryable` is asserted only as a boolean. Expired documents use skew-aware offsets. VRC-ISS-020 accepts an idempotent receipt or a task-specific refusal. DUP-103 requires `carrier:openPayload`. A hold asserts `expects` and `continuation` only when no status task is declared.
- **HTTP status mappings are SHOULDs.** 2PC-007's 409 for `idConflict` is `httpStatusShould`: advisory at Tier 1, failing under `attested` at Tier 2 (the MUST is the `idConflict` rejection itself, SPEC.md:1021; the status mapping is binding https 0.3 text at 135 and 154).
- **Window-independent rows stay Tier 1.** TIME-013, 014, 022, 023 and 024 omit or do not depend on the window, so they carry no `profileWindow` flag.
- **Window-relative native vectors.** TIME-101 (stale), TIME-102 (future), DUP-005 (resend after the record window) and TIME-104/105 are relative to the declared window, not to hard pins, because the framework sets no numbers.
- **BND-002 stays Tier 1, gated on a transport identity.** The binding says the token-to-VID mapping is deployment-defined (binding 0.3 spec.md:129) and the 422 and 200 are the status mapping's SHOULD (:135), so the vector runs where the adapter declares `optional:transportIdentity` (as ID-002 does) and judges the statuses as advisories; a deployment whose HTTPS door authenticates no sender is SKIP, not a failure. Rejected: Tier 2 (the identity cross-check is the binding's MUST, :124 and :131, once the transport authenticates a sender) and leaving it ungated (it asserts a mapping the text leaves to the deployment).
- **A rejection's error reply is a SHOULD.** SPEC.md 7.2 requires the rejection and states the error reply as a SHOULD (:1071; a MAY at :1196), so the vectors that judge a rejection by `noSideEffect` and state carry `errorReply: "should"` (ENV-006 to 009 and 011, ID-001 and 002, LIF-002 and 003, CTRL-001 to 003, ERR-004, the PRF and TIME rejection rows, DUP-002, 003, 005, 009 and 010 and the item 11 rows, DIS-010, 011 and 017, VRC-PRO-004 to 006, 014 and 015, CEX-019, 020, 031 and 036). A missing reply is an advisory (a failure under `attested`); a sent reply is still checked for its code. Rejected: `any-refusal` (it never checks the code, so ERR-004's mutant that answers a wrong code would pass) and a CLARIFY per vector (the text is not open, only SHOULD). ENV-010 keeps the mandatory reply: SPEC.md:756 puts it inside the MUST.
- **The age vectors need a declared window.** DUP-005, TIME-101 and TIME-105 cross a maximum age the text does not set (SPEC.md:1035, :1043), so they need `window:declared` and are SKIP otherwise; the profile pin is never a fallback, because that would measure an implementation against a number the framework does not state. TIME-101's citation is SPEC.md:1014, :1035, :1043 (SPEC.md:1023 does not mention a maximum age). The outcome stays `expired`, as the task force's freshness fixtures use it for the same edge.
- **CEX-001 allows the courtesy acknowledgement** (SPEC.md:217-223): silence or exactly one `#response` with payload `{}`. CEX-023 is CLARIFY spec-inconsistent: noMatch for an unheld type is distinguishable from the consentRequired a held type gets, which the query specification also forbids (:84, :141-142); the same tension as CEX-024.
- **TC-012 is CLARIFY vector-overreads.** The text is clear (consumer 6 and 7, task-consent/request 0.1 spec.md:154-155) but the vector asserts `prompted`, which presumes membership of an `approverSet` the policy sets (:197) and the harness does not declare.

## 2. Clock, run salt and declared windows

- **`clock` or `clockFree`, exactly one.** An adapter that declared neither would be indistinguishable from a settable one that forgot to say so, so the runner refuses it.
- **Rebase mode** takes real time to the whole second and keeps each vector's relations to its clock start, including absolute `issuedAt` and `expiresAt` in send parameters. A calendar-invalid instant (Feb 30) is left alone so it stays malformed. Literal forward offsets of at most 10 s are waited out in real time, so the same-document duplicate rows and the corrected-resend rows are measured without moving the implementation's clock.
- **`exactClock`** marks the fixture rows that straddle an edge by a millisecond (and TIME-006, one second from an edge); they need a settable clock.
- **Fixture rows are not re-derived.** The TF freshness rows state absolute instants for the profile window. They are kept as they are (`profileWindow`) and are SKIP for another window, with the matrix naming them. The window-relative native vectors carry margins of seconds so they are measurable in rebase mode.
- **A runner-given window is a claim.** If the implementation enforces another, the window vectors fail.
- **Run salt.** `deterministicId(vectorId, name, salt)` also maps the `urn:uuid` literals inside raw fixture documents through the same hash, so equal ids stay equal. Without a salt the ids are the unsalted ones.

## 3. Framework groups

- **Order of building.** Cheap framework groups first, then NS and AUTHZ on the VRC hold and issue paths, then witness-share (WSH) and the task-digest group (TD) on one bundle builder. TD runs black-box through the witness-share carrier because no other framework task carries a digest.
- **CLARIFY choices.** ERR-005 (the default `retryable` is a SHOULD), ERR-008 (no sentence says an error is never answered), AUTHZ-002 (`permissionDenied` is a design rule), DUP-007 and DUP-008 (fail closed: design rule, specification silent), CTRL-004 (the order of the 7.2 check list is not normative).
- **Fault capabilities.** DUP-006 to 008 need `restart` and `fault.claimStore`; a platform that cannot fault its duplicate store reports SKIP.
- **Payload-independent tampering.** Framework vectors tamper with `/threadId` after signing, not with a payload member, so they assume no payload shape. The carrier payload comes from `validPayload`, with invalid and extra-member variants derived. The proof check uses the provisioned DID document.
- **Identity checks follow the transport.** Framework 7.2 item 6 applies only to an identity the transport authenticates, so ID-002 and ID-004 need the optional `transportIdentity` capability; ID-003 checks issuer against proof signer.
- **Nothing to address on an undecodable document.** Thread and recipient advisories are not raised on a `malformedRequest` refusal.
- **ENV-010** asks for the carrier's own family at another MAJOR (`$carrierMajor`), not a fixed family.
- **BND-001** accepts 404 or 405 for another path: a server that serves a website on GET at every path answers 405, and the binding does not settle which.
- **Discovery version.** Discovery vectors run against 0.3 or 0.4, whichever the implementation declares (`$discovery`, `$discoveryResponse`); the request rules are the same text in both, so each vector cites both, DIS-013 runs against 0.4 only, and a 0.3 answer that carries `expiryHorizonSeconds` fails the closed 0.3 response schema. SPEC.md:1537-1540 designates discovery 0.2 and the binding names 0.1, a task-force question outside these vectors.
- **Mutants that really change the vector.** The `terminalErrorAccepted` mutant skips both terminal type checks, so each terminal-type vector names a mutant that changes its outcome.

## 4. Discovery, HTTPS binding and two-phase commit

- **One source for discovery.** The reference adapter answers discovery from the same list it declares in `supportedTypes`. The harness checks the answer against that list with its own pattern matcher (an independent reading of the grammar) and against the response schema. DIS-012 and DIS-013 prove an advertised window by sending documents at its edges; they are gated on `discovery.acceptanceWindow` and `discovery.expiryHorizon`, so an adapter that advertises no window is not failed.
- **The harness never speaks HTTP.** The adapter does, and reports status and content type. `--no-https` on the example server models an in-process-only adapter, for which BND is SKIP.
- **2PC runs on the `issue` task.** The coordinator's truth is the outcome, never the vote: the mutants answer on prepare, store despite abort, and answer while in flight.
- **Group ids may start with a digit** (`2PC`).
- **TD-001 to TD-006 test the pairing rule, not the receipt encoding.** SPEC.md 4.9.3 (:545-559) decides the digest input, the multihash and the byte comparison; the receipt's `vwcDigestMultibase` is a profile member whose schema admits base58btc and base64url (docs/10 section 5.1), so TD-001 to 005 assert acceptance and one stored credential, not the receipt digest (WSH-001, 011 and 017 keep it as the profile's own check). Rejected: keeping the receipt pointer (a receiver that answers the same digest in `u` conforms and would fail a vector about something else).
- **TD-004 and the altered initiating document stay schema-valid.** The nested proof sits under `payload.ext`, and `alterInitiating` adds a namespaced `ext` member, not an undeclared one, so a receiver that schema-validates the evidence still reaches the digest rule (TD-004, TD-006, WSH-007 step 1, WSH-012).
- **TD-005 has one share, in base64url.** `DigestMultibase` admits only base58btc `z` and base64url `u` (framework schema; SPEC.md:553, :2195), so the base16 share is not a valid citation and is removed from TD-005 and WSH-024 (WSH-024 shares a base64url and a base58btc credential on one exchange; it stays CLARIFY, permissive reading).
- **WSH-012 is true whether or not the consumer implements SHA-512.** The citation is also altered, so a consumer that does implement the hash refuses it by recomputing (SPEC.md:552, :557); a consumer that does not implement it must not recompute and must not compare by id. **WSH-017 is CLARIFY vector-overreads:** the idempotence is a profile SHOULD (docs/10 section 8) and a redelivery under a new id is a different document for SPEC.md:1021.
- **WSS-010 and WSB-004.** WSS-010 cites the session specification's mutating level and SPEC.md:92, :1021, :1055 (the prior result is returned, never `taskFailed`). WSB-004 is CLARIFY spec-silent: the submit specification fixes only the challenge binding as the first check (spec.md:216), so the order after it and the code under the witness's own policy are open.
- **Matrix rows** merge runs that share `capabilities.implementation`; mutant runs keep their own name so they never merge into the reference row.

## 5. Ceremony documents (CER) and 3b-DTG (TC, CEX)

**The ceremony family is declared by the adapter, not hard-coded.** An implementation may serve private URN types and a begin payload the suite cannot assume, so `capabilities.ceremony` carries the Type URIs, an optional status type and payload templates. The reference uses test types (`https://trusttasks.org/spec/conformance/ceremony/{begin,approve,reset}/0.1`), like the carrier.

**Proposer approval is a declared property** (`ceremony.proposerApproves`, required, no default). Whether a begin counts as the proposer's approval is unspecified, and one implementation records none at begin. Rejected: sending the proposer's approval in every vector (it would make gating vectors depend on a repeat approval being a no-op, which is CLARIFY CER-004) and a default of `true` (it hides the question). Steps carry `when: {proposerApproves}`; a skipped step keeps its position so `sameErrorAs` and `same: previous` keep their meaning. CER-014 pins the declaration to behaviour in both directions (mutant `cerProposerApprovalFlip`). The non-vacuity check runs every mutant in every reference configuration its vector runs in.

**Hold rule instead of a pinned `continuation`.** SPEC.md 8.6 states a value only where no status task is offered. `expect.hold` asserts `resubmit` only where `expects` names the request's own type; CER-002 is SKIP for an adapter that declares `ceremony.status`, and CER-015 and CER-016 require it. Under the status variant every hold must name the declared status task. CER-015 gates (SPEC.md 1417); CER-016 (the status query is answered and records nothing) is CLARIFY.

**Other ceremony choices.** A reset is a document, not a trigger; the states it needs are reached with `ceremonyDeadline` and `ceremonyEffect`. Retention is compared to the exact bytes sent, and CER-013 sends a pretty-printed, reversed-key-order document so a canonicalising store fails. The quorum rule itself is not asserted: the `registry` vectors reach their holds through `quorum` steps expanded from the essential governance the adapter declares (the authority set and k), and CER-017 to 019 (`candidate`) measure behaviour against that declaration; the `ceremony-design` vectors that name two administrators are advisory ([decision 39](decisions/04-ceremonies-governance-and-exceptions.md#d39); docs/04 section 11.4). The default fail reason is `storeFailed`, not asserted by a vector. CLARIFY: CER-004 (a SHOULD), CER-007 (a MAY), CER-010 and CER-012 (closed reason vocabulary), CER-013 (verbatim retention).

**3b-DTG.**

- **Binding values come from a helper action, not from the hold.** The task-consent specification fixes what the digest covers, not how an implementation mints or stores the challenge. Reading it from a hold's `ext` would be implementation-specific, so `consentBinding` returns `{challenge, payloadDigest}`. The runner does not validate a helper action's reply as a document.
- **The pending request is a ceremony**, reusing the ceremony family: it is held one approval short of the declared k (a `pending` quorum step), and the k-th member of the declared authority set decides.
- **Tier 1 gates only what the task specifications state;** stricter rules (a credential about someone other than the holder, a presenter that is not the sender) are Tier 2, because the specification leaves acceptance to the consumer.
- **Accepted `issue` and `present` are silence**, because the registry text defines no response document; the durable record is the evidence.
- **Nonce member name.** The text says the proof carries "the same nonce and domain"; Data Integrity names the member `challenge`. The vectors send `challenge` and `domain`, which is why CEX-011 to 014 are CLARIFY.
- **No clock offsets,** so both groups are measured in rebase mode too.
- **TC-018** accepts either the `pending` response or a hold that meets the hold rule (expectation member `orHold`), and stays CLARIFY.
- **The test credential is typed `MembershipCredential`,** the DTG catalog tag; `VerifiableMembershipCredential` is named as not canonical by the vmc specification.
- **Query, offer, request and granted.** Helper actions `holdCredential`, `verifierTrust` and `queryDecision`, and observe kind `deferral`, are each an optional capability, so a platform that cannot honestly provide one gets SKIP, not a guess. CEX-024 is CLARIFY because the text contradicts itself (a deferred query must be answered `consentRequired`, yet held-but-not-consented must be indistinguishable from `noMatch`); CEX-022 keeps `consentRequired` gating because that sentence is explicit. CEX-025 and 026 are CLARIFY (pre-trust is the holder's policy; nonce and audience names are not fixed). Not tested on purpose: whether the holder shows the `purpose` to its human (no black-box observation exists), and the SHOULD on rate-limiting queries.

## 6. Witness-share profile

The profile ([10-witness-share-profile.md](10-witness-share-profile.md)) mirrors keyring-wallet's wire members exactly, because the wallet is the only implementation. Registry-style front matter is used. `targetFrameworkVersion` 0.6.0 matches `witness/session` 0.2. `issuedAt` REQUIRED is a profile choice (the wallet always sets it). `exposure` and `retention` are omitted because the wallet does not determine them. The extended error code follows the registry convention (`vrc/relationships/witness-share:notAccepted`). WSH-008 and WSH-009 are Tier 1 because they follow framework 4.9.4 items 3 and 4 for a consumer relying on a citation. WSH-022 (terminal-to-VWC binding) and WSH-023 stay reserved: 022 needs a rule the profile lists as not made, and 023 has no text.

## 7. Ceremony receipts (RCPT)

- **A verifier method, not a wire exchange.** The receipt specification's verifier rules have no wire output, so the optional adapter method `verifyReceipt` (capability `receiptVerify`, named after `proofVerify`) measures them. Rejected: dropping the verifier rules. This departs from the pure black-box principle, which is why it is optional.
- **Verdict vocabulary.** Four values (`complete`, `incomplete`, `unverifiable`, `invalid`); the suite pins only the specification's three distinctions (reject, could not verify, not complete). Where the text allows more than one verdict a vector lists the accepted ones. This is the suite's reading, not a proposal to the task force.
- **The definition is in the registry shape**, on a private authority (`conformance.example`), as SPEC.md:986 requires of a private definition. **Role bindings are an input**; absent bindings are the case where the text requires "could not verify".
- **Tier 1 only for MUSTs;** there is no named receipt profile, so nothing is Tier 2. Each negative vector is built so that only the rule it names catches it.
- **One group, RCPT,** avoids a clash with the CER ceremony-document group. CLARIFY rows and their open points are in docs/04 section 11.6.
- **Not covered:** the `ceremony` member on ordinary documents (CRM), the recorder side, nested ceremonies and `maxDuration`, `enactmentPrivacy: blinded` (the receipt cannot express it), evidence for failed, aborted or expired enactments (undefined), a receipt proof purpose (none stated), and cryptosuites other than `eddsa-jcs-2022`.
- **Specification gaps found:** no wire output for a verdict; salt and role-binding distribution are out of band and the envelope member has no salt; the receipt targets framework 0.5.0 while the suite pins 0.6.0; the Rust crate rejects things the text states as no rule (wrong `typeUri`, undeclared step, round beyond `maxRounds`, an evidentiary role as issuer); the framework forbids rejecting on the `ceremony` member alone while its schema is closed; the registry has no valid full receipt example.
- **Open questions:** whether a malformed `ceremony` member is rejected or ignored; how a recorder learns the steps; whether the suite's word "receipt" for the VRC issue acknowledgement should be renamed to avoid the collision; minimum hash support and the verdict for an unknown multihash; which Tier 2 candidates would become `attested` rules.

## 8. Out-of-process adapter client

- **The wire method set is exactly the in-process dispatcher's** (`dispatch` in `src/adapter/contract.ts`), so the two paths cannot diverge. Adapter failures keep the adapter's own message unchanged, so a vector's failure text is the same in process and over the wire; the equivalence test compares whole result lists.
- **stdio** is one process per run and tier, answered strictly in request order. **HTTP** serialises calls on the server, because an adapter holds one conversation's state.
- `http:<url>` is accepted in four spellings because the flag form is ambiguous about the scheme.
- **Not built:** authentication on the HTTP transport (the example server binds 127.0.0.1), TLS client settings, batching, and parameter-validation errors (-32602).

## 9. Not covered yet

The IUT-initiated direction of `propose`, `issue`, witness-share and ceremonies (the reference adapter alone now has it, for the ceremony-scenario dry run of [docs/25](25-ceremony-scenarios.md); no platform adapter does); the discoverer side of discovery (an implementation that sends discovery must not act on an unauthenticated answer), which needs an IUT-initiated direction in the contract; a vector for the ceremony `fail` default reason. The full open list is [07-status-and-open-questions.md](07-status-and-open-questions.md) section 4.
