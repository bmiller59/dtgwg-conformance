# Open gaps: good first contributions

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

This page lists what is not done yet, with what each item needs, so you can pick one. It is generated by `scripts/community-open-gaps.ts` from the data in `docs/community/data/` and the scenario files; to change it, change the data and run `node --experimental-strip-types scripts/community-open-gaps.ts`. A test fails when the page is stale or the data disagrees with the scenario files.

Snapshot of 2026-11-23. Every task specification involved is draft. Ceremony figures are completion of scenarios run together, never conformance. Before you start, read [how to contribute](contributing.md): in particular, a point where the specification text is open is discussed with the task force and is not asserted in a vector.

### What blocks the open scenarios

59 scenarios have no completed run. Each is named by exactly one blocker below, with its class (A the implementation differs from the specification, B the vector reads more than the text says, C the specification is open, D the harness or a stand-in).

#### Issuer seat on the wallet (mutual attestation, request from the issuer)

- **Blocking class:** D.
- **Scenarios (4 of 163):**
  - `FC-MAT-001`: mutual attestation: each person issues a credential about the other (attest-first, attest-second); both keep ...
  - `FC-MAT-002`: mutual attestation with no order: the second person attests before the first does, and the ceremony completes ...
  - `FC-MAT-003`: mutual attestation, simultaneous: both offers and both requests are exchanged before either credential is ...
  - `FC-CEX-001`: an issuer's offer is answered by the holder's request on the offer's thread and that by the issue on the same ...
- **Blocked because:** The wallet has no issuer role for credential-exchange: it never sends an offer or an issue, redeems an offer over HTTP, and receives issues through its persona inbox. So it cannot take either mutual-attestation seat, and VTI is not a person seat. FC-CEX-001 needs the same issuer seat on the wallet side.
- **Needed:** An issuer seat on a wallet adapter (a platform feature, not a specification fix), or another platform that can take a person seat, so that two independent parties can play the two seats. A stand-in that produced the outcome itself would be a false completion and is not wanted.
- **Where to start:** [`docs/27-kw-vti-ceremonies.md`](../../docs/27-kw-vti-ceremonies.md), [`vectors/ceremony-scenarios/fc-mat.json`](../../vectors/ceremony-scenarios/fc-mat.json), [`vectors/ceremony-scenarios/fc-cex.json`](../../vectors/ceremony-scenarios/fc-cex.json).

#### Wallet-to-wallet runs (relationship credential and witness share)

- **Blocking class:** D.
- **Scenarios (6 of 163):**
  - `FC-VRC-001`: propose accepted, each party delivers its credential, each delivery receipt matches, both parties read ...
  - `FC-VRC-002`: propose declined: the responder answers with propose:declined and both parties read declined
  - `FC-WSH-001`: witnessed exchange in the order session, submit, share, issue: each party's credential is minted by the ...
  - `FC-WSH-002`: the same exchange in the opposite order: both credentials issued first, then the sessions, then the shares, ...
  - `FC-WSH-003`: a submission bound to the challenge of another session of the same party is refused with ...
  - `FC-WSH-004`: a party that shares the credential it received back to its sender is refused with ...
- **Blocked because:** Two wallets playing both sides is a separate category and is never added to the VTI-wallet figures. The propose step is not reachable from a runner step in the wallet adapter (no ceremony kind for it), relationship-credential delivery and the witness share run on stand-in crypto, and there is no witness party (the reference adapter lists no witness role; the witness server is a containerised DIDComm service).
- **Needed:** Runner support for wallet-to-wallet: an initiate for the propose step in the wallet adapter, a witness party the runner can seat, and real rather than stand-in crypto for delivery. The smallest next step is FC-VRC-002 alone.

All the vectors of this set are advisory (channel `proposed`); none is promoted. How the set is built and measured is in [vector completeness](../37-vector-completeness.md). Covered means a vector exists. It does not say any platform passes it: per-surface agreement is reported per run in the dated results pages, never added across surfaces.

- **Blocking class:** D.
- **Tasks:** `vta/credentials/issue 0.2`.
- **Blocked because:** The response schema (allOf with unevaluatedProperties) is one no schema builder in the suite can satisfy, so the generator cannot build a response for the reference adapter to give.
- **Needed:** An extension of the response builder, or a hand-written vector with a checked response.

#### Tasks with no negative vector (3)

- **Blocking class:** not classified A to D in the source.
- **Tasks:** `auth/oob/grant 0.3`, `auth/oob/identify 0.1`, `trust-task-error 0.6`.
- **Blocked because:** No negative could be built from the specification text (a required member, a closed payload, a wrong-type member or an invalid example the specification ships).
- **Needed:** A negative case read from the text, with the clause quoted, and a mutant that it must catch.

#### Positives that pass on any non-envelope answer

- **Blocking class:** D.
- **Blocked because:** A positive is weak when it passes on any answer that is not an envelope error. It is not asserted where the task changes state, the request names an identifier or free text, or a state-dependent code can legitimately fire. See the per-family table below.
- **Needed:** Adapter state: a way for the adapter to seed or name the objects a request refers to (identifiers, fixtures), so that the success response can be asserted. This is the largest single block of work.

#### Vectors that need a disposable deployment

- **Blocking class:** D.
- **Blocked because:** A mutating or destructive vector is not run unless the run names a disposable deployment, so it is reported SKIPPED-SAFETY and counted nowhere.
- **Needed:** A runner configuration pointing at a disposable deployment of the platform (a container or throwaway database), then runs of those vectors.

#### Refusal steps accept only two codes

- **Blocking class:** D.
- **Blocked because:** The refusal steps of the other coverage vectors accept only the malformed-request and permission-denied codes. Accepting a task's own standing code there would let one deliberately broken variant of the reference adapter (noPayloadValidation) pass unnoticed.
- **Needed:** A way to accept a task's own standing codes without losing that check, for example a mutant that tells the two apart.

#### Witness vectors that need the authorised capability (46)

- **Blocking class:** D.
- **Blocked because:** 46 witness vectors require the adapter to declare the optional capability authorised, meaning that its policy accepts the harness actors. An adapter that does not declare it sees them SKIP.
- **Needed:** A platform adapter that declares the capability honestly, with the evidence for the declaration.
