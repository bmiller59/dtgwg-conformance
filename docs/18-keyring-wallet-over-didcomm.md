# 18. keyring-wallet over real DIDComm

> **Status: draft proposal.** This is a draft proposal for discussion and review by the DTGWG (Trust over IP Decentralized Trust Graph Working Group). It is not an adopted or endorsed standard or test suite.

Adapter `keyring-wallet-didcomm` (`src/adapters/keyring-wallet-didcomm/`); run record `<results dir>/runs/2026-11-15-kw-didcomm/`.

## 1. What it measures

The shim adapter (`src/adapters/keyring-wallet/`, [docs/05](05-reference-implementations.md)) puts an in-memory sender and handler registry under the wallet's `Carriage` port, so nothing is packed or delivered. This adapter removes the shim: a real Credo agent (askar-nodejs, HTTP inbound on loopback) runs the wallet's own `ceremony.setupTrustTasksInbound` inside the wallet's jest, and the suite's DIDComm carrier ([docs/13](13-didcomm-carrier-and-witness-server.md)) reaches it by out-of-band invitation. Packing, authcrypt, connections, transport and the wallet's own replies are real. The adapter declares bindings `didcomm`, `didcomm-v1` (or `didcomm-v2` for the v2 row). Both rows declare `platform: keyring-wallet`: the wallet's exceptions apply to each, an exception a row no longer meets fails as stale (`src/runner/suite.ts`), and a recorded run of either row gates keyring-wallet ([docs/15](15-keyring-wallet-didcomm-v2.md#how-the-suite-measures-the-v2-row)).

## 2. Parts

- `kw-didcomm-agent.ts`: builds the agent from the wallet's nested Credo copies, with a 40-line HTTP inbound transport bound to the nested `@credo-ts/didcomm` (the hoisted `@credo-ts/node` transport resolves the other copy and fails DI), publishes a multi-use OOB invitation.
- `kw-didcomm-host.jest.ts` + `../keyring-wallet/kw-host.jest.ts` (`KW_REAL_AGENT` mode): the host. One code path serves triggers and observes for both adapters (policy, consent via `respondToRelationshipProposal`, `holdCredential`, `queryDecision`, observe handled/stored/deferral, clock, snapshot/diff, reset, restart, emit). In real mode the app's own duties that the shim did inside `send` run on a 50 ms tick (create the relationship-DID record when a connection forms; apply the proposal policy).
- `adapter.ts`: the suite side. Identity mapping as for the witness server: each sending actor (A, X, Q, W) gets a connection and a carrier agent, harness did:keys are rewritten to connection DIDs and back, documents carrying a proof are signed again (a valid proof stays valid, a proof the harness had broken is broken again; R and S, which have no connection, are signed with the suite's own keys). `from spoof` sends on the named actor's connection; `from none` sends an anoncrypt message to the wallet's service (no sender), which reaches the wallet's real "arrived without an authenticated connection, retained, not processed" branch. Triggers that make the wallet send (consent, queryDecision) collect what arrives on the carrier.
- `launcher.ts`: starts and stops the host (free ports per launch, stop file, `/shutdown`, SIGKILL of its own child after a grace period).
- `compare.ts`: per-vector comparison of two runs.

Control plane: loopback HTTP JSON-RPC to the host (the shim host's own contract). It cannot ride DIDComm because the triggers are acts of the wallet's person (accept, approve), local state seeding and clock control. Restart is a real agent shutdown and re-initialisation over a file-backed store.

## 3. Declared stand-ins and limits

- Emit: the producer builders use no transport; in real mode they run in the host against the shim agent (same code as the shim row), so emit results equal the shim's by construction.
- The clock is the host's faked `Date` (jest fake timers, as in the shim row).
- Bytes that are not a JSON object cannot be placed in a DIDComm attachment: such sends are `refused` at the carrier (as in the shim row).
- Reply proofs: replies are returned with DIDs mapped back to the harness's names; the wallet signs none of the replies in reach (finding 3), so no reply proof is invalidated by the mapping.
- v2: the carrier is the suite's own `src/carriers/didcomm/carrier.ts`, which carries the DIDComm v2 fix of `conformance/observe-oracle-v2` (RFC 0008 thread ids, rotated peer DID; docs/13 section 8). The adapter first held a private copy of it (`carrier-v2fix.ts`); the copy was deleted at the final merge and the adapter imports the real carrier. Anonymous (`from none`) sends are not implemented for v2.

## 4. Findings

1. **No verdict differs between the shim and real DIDComm.** The figures in this item are historical (on the 361- and 368-vector core sets, 2026-11-15; superseded by `<results dir>/runs/2026-11-15-final2-kw-didcomm/`, whose figures are generated in Coverage and on results/platforms/keyring-wallet.md). Compared over core (361 at each tier when the adapter was built; 368 on the final merged tree, the 7 new CEX-033 to 039 being SKIP on both), emit (183), emit-more (75) and the proposed channel (23). The shim did not hide or invent a verdict for any vector in reach (Tier 1: 38 PASS / 28 CLARIFY / 85 fail / 210 SKIP on both, 217 SKIP on the final tree; Tier 2: 38 / 26 / 76 / 221 on both, 228 on the final tree). On the final merged tree the "85 fail" are KNOWN-FAIL on both rows: the row declares `platform: keyring-wallet` in its capabilities, and an exception keyed on the platform applies to every row that declares it (`src/runner/suite.ts`; the earlier run showed the same 85 as FAIL because the row name differed). The per-vector comparison of the final runs (368 of 368 same at both tiers) is in `<results dir>/runs/2026-11-15-final-kw-didcomm/diff-core-t1/` and `diff-core-t2/`. The v2 row declares the same platform, so the shim-derived exceptions apply to it too. The recorded v2 folder (`2026-11-15-final2-kw-didcomm/v2-core`) predates that declaration, so its failures there are not excused and it is shown as a not-gating experimental note. Over v2 ENV-003 passes: the wallet's own v2 binding drops a carried document with no `id` before the pinned runtime sees it (`TrustTaskEnvelopeV2Message`, document getter, at `bifold` 7e14c5124), so the difference the ENV-003 entry excuses sits in the v1 and shim path only. A v2 run recorded with the declaration showed the entry stale; the entry now names the v2 row in `notOn` (docs/04 section 8), so v2 is judged without it.
2. **State persists across vectors on a real wallet.** The shim builds a new store for each vector; the real agent keeps what it retained. Retained documents and relationship-DID records changed later verdicts: with only the relationship records wiped, 6 passing vectors (VRC-PRO-001/002/003, VRC-ISS-006/011/013) failed because an earlier accepted proposal on the connection made the next one an "upgrade exchange" (`relationshipMismatch`); with neither wiped, VRC-ISS-004/006 returned `proofInvalid` where the shim returned `notAccepted`. The vectors assume isolation; a real adapter must reset the implementation's retained state per vector. (Development observation, runs not kept.)
3. **The wallet's replies carry no `proof` member; that is real, not a print artefact.** Over the wire, all 338 replies in `core-wire-trace.jsonl` are unsigned: 100 `vrc/relationships/propose#response`, 163 `trust-task-error`, 75 conformance widget responses. Source: `ceremony.ts` comments ("The propose legs ... their proofs are OPTIONAL and unsigned today", "Receipt proofs are OPTIONAL (we send ours unsigned)"); only documents built with `signDocumentProof` (issue delivery, witness-share, credential-exchange present) are signed. DIDComm v1 authcrypt authenticates the sender. No vector's verdict changed over the real wire, so the suite does not today measure signed replies.
4. **The sender-less path is real.** An anoncrypt message reaches the wallet with no connection and is retained, not processed (host log line from the wallet's own handler); the `from none` vectors behave as in the shim row.
5. **v2 works for the wallet** with the flag and constructor options the spike named, headlessly. 338 replies over v2; see the run README for the one differing vector (a carrier artefact) and the unimplemented anonymous send.
